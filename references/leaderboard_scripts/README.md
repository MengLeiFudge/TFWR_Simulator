# Leaderboard Scripts

这个目录承载两类长期资料：

- `lb_*.py`
  - 具体榜单脚本真源
  - 只保留必要实现说明、关键魔法数字来源、当前成绩摘要

- `lb_*.md`
  - 具体榜单的策略文档
  - 承接目标、基线、版本结论、失败对照、下一步方向、候选策略

`lb_start.py` 例外：

- 它是部署时生成的入口脚本
- 不属于具体榜单的长期策略真源
- 不需要也不应配套 `lb_start.md`

## 共用打榜注意事项

以下内容承接并改写自历史提交 `00f01b30` 中 `AGENTS.md` 的 `## 第二阶段优化器关注点`，但语境已经切换到当前真实游戏 oracle workflow。

1. 先研究决定 leaderboard 成绩的收益结构，不先做语法级微调。
   如果一个榜单的主收益来自 companion、连通块、全图并行、或某个特殊结算倍率，就应先围绕这个主收益设计路线，而不是先卷局部 tick 小优化。

2. 伴生、高倍率机制、版图布局、路径和回访节奏通常优先于局部实现细节。
   对依赖 companion 的榜单，没吃到 companion 往往就接近没有有效收益；对不靠 companion 的榜单，应优先围绕真正的结算机制做设计。

3. 世界大小和版图布局通常是第一优先级决策变量。
   默认世界大小不一定是最优解；应主动评估小图降移动成本、大图拉高并行吞吐、穿边、跨边界 companion、块划分等收益。

4. 复杂机制路线必须和低调度成本吞吐路线做基线对照。
   `wood` 的 `main3` 证明：即使榜单表面上依赖 companion，也不能直接把搜索空间锁死在“稳定 companion / support 网络 / reroll 最优伴生”。必须先测一个低复杂度、低寻路、低协调、全图并行的暴力吞吐基线，例如固定棋盘、按列扫、只做成熟收获和重种。如果这种路线已经明显超过复杂机制路线，说明之前的主瓶颈不是倍率没吃满，而是寻路、claim、support 初始化、reroll、等待和跨无人机协调成本太高。该经验优先适用于 `wood`、`hay`、`carrots`、`pumpkins`、`sunflowers` 这类“主资源吞吐 + 可选倍率机制”的榜单；不应直接套到 `maze` / `dinosaur` 这种核心目标由特殊状态机或路径目标决定的榜单，但仍要保留“低调度成本基线先验”。

5. 必须明确区分 `200t` 操作和 `1t` 判断的成本模型。
   默认优先“多判断、少误操作”。只有当主流程已经稳定、判断不再明显减少昂贵动作时，才考虑进一步削减这些廉价判断。

6. 水、肥、重种、reroll、support 改写都要按收益 / tick 成本评估。
   这些动作不能因为“可能有帮助”就默认加入；应明确它们试图解决什么瓶颈，以及实际是否值得。

7. 不同 leaderboard 的目标函数和瓶颈不同，不能硬套统一模板。
   `fastest_reset`、`maze`、`pumpkins`、`sunflowers`、`wood` 的最优策略结构很可能完全不同；先识别主瓶颈，再决定搜索空间。

8. 验证节奏必须分层。
   默认先做单次验证，确认方向没有明显慢几十秒；接近基线后再做多 seed 对比；只有差距已经足够小，才值得跑更长流程看均值。
   请求启动后不能前台空等 `run_real_game_script.py` 结束；长流程默认用 `--request-only` 只写入 state 请求并立即退出，不等待 idle、不抓日志、不进入轮询，然后用 `--status-only --status-lines <行数>` 短命令读取三类文件：游戏 `output.txt`、BepInEx `LogOutput.log`、状态机 `state.json`。其中 `output.txt` 用来确认完成轮和脚本 `print()`，`LogOutput.log` 用来确认每秒 `item_snapshot`、资源速率、实时估算和模组错误，`state.json` 只用于确认请求状态。打榜脚本每完成一轮必定新增一行输出，如果连续 `30s` 没有任何游戏输出和模组输出，应停止本次请求并判定该候选卡住或明显低效。游戏内是否变快必须优先看脚本输出的 `time=`、阶段切换日志、资源增量和 leaderboard summary；如果多无人机导致实际加速倍率低于 `200x`，这是验证环境现象，不能直接判定策略变慢。
   排行榜完整统计是约 `2h` 多轮取均值；估算只在第一轮尚未完成时启用。第一轮完成前，runner 必须根据 `LogOutput.log` 的 `item_snapshot` 实时输出 `progress_estimate`；第一轮完成前是否继续等，只能用 `eta_game_time` / `eta_game_seconds` / `game_tick` 对比当前最好成绩和 #1 成绩，不能用 `eta_real_time` 判断策略优劣。`eta_real_time` 只用于知道验证命令大概要占用电脑多久。若预估游戏时间已经明显慢于当前最好成绩，应立即停止并记录为弱候选；若预估游戏时间明显优于当前最好成绩，即使现实还要跑几分钟，也可以继续跑到首轮结算。第一轮完成后，判断依据切换为已完成轮的平均时间，不再拿资源 ETA 当主结论。
   运行任何 `lb_*.py` 真实验证时，`run_real_game_script.py` / `real_game_runner.py` 默认至少等待 2 条新增 `run=` 输出。若最近两轮差异不超过 `10%`，用当前均值停表；若最近两轮差异超过 `10%`，继续运行直到最近两轮进入 `10%` 内再停。显式传 `--max-leaderboard-runs 0` 表示不按轮次稳定性停表，通常只用于刷完整官方统计或专门观察长尾均值。
   `simulate()` / `leaderboard_run()` 的最后一个参数是模拟速度上限，不是保证倍率；当参数设得很大，例如 `10000`，真实速度会受电脑性能和脚本计算量限制。高计算型脚本出现现实 `1s` 只推进游戏内 `10s` 这类情况是正常现象，不能用外层墙钟直接比较策略。

9. 长流程验证应允许动态停表。
   脚本应主动打印足够细的阶段日志，例如阶段名、`time=`、关键资源、无人机数、目标值。代理验证时可以根据这些日志判断方向已经明显无效、已经达到目标、或需要切换探针，并提前停止；不得机械等待外层 `1min`。如果提前停止，必须把停止依据写成“游戏内阶段时间 / 资源进度 / output stall”，不要写成单纯墙钟耗时。

10. 真实游戏结果优先于仓库内推断。
   `output.txt` 是最高优先级完成轮证据；`LogOutput.log` 是第二优先级运行进度证据，模组请求运行中应每秒输出 `item_snapshot` 展示当前所有物品数量；`state.json` 是控制面证据，只确认请求是否 `running` / `done` / `failed`。如果 `output.txt`、`LogOutput.log`、真实存档行为与当前脚本推断冲突，应优先修认知，而不是硬保留旧结论。

11. 所有魔法数字都必须注明来源。
   来源至少应指向以下之一：
   - 真实游戏常量
   - 反编译源码
   - probe 实测结果
   - leaderboard 基线数据
   - 明确的成熟 / 回访节拍推导

12. 失败路线也要长期留档。
    已经验证明显偏慢、冲突过高、收益不足的方向，应写进 `lb_xxx.md` 的“失败对照”，避免后续重复试错。

## 外部候选 `.py` 评估流程

这套流程适用于用户提供新的外部存档脚本、参考脚本、别人榜单脚本，或在 `Save0/` 参考目录里发现新的 `.py` 文件。

1. 先读取脚本内容，再判断它是什么。
   不允许看到文件名像 `lb_xxx.py` 就直接运行。必须先确认它是打榜入口、被打榜入口调用的目标脚本、普通测试脚本、工具库，还是混合脚本。

2. 先修运行入口，再修策略目标。
   如果是打榜候选，应改造成通过已有 `lb_start.py` 和已有 `lb_xxx.py` 运行；如果是测试候选，应改造成通过已有 `test.py` 运行。发现目标条件明显不符合榜单，例如 `wood.py` 用 `Wood > Hay` 提前退出，不能直接判死刑，应先把目标改成真实 leaderboard 目标再复测。

3. 禁止把外部依赖直接新增进真实存档。
   外部脚本依赖 `utils.py`、`move_utils.py` 等文件时，应读取依赖内容并把必要逻辑内联或迁入仓库真源；真实 `Save0` / `gamesave` 只能覆盖既有文件内容，不能新增、删除依赖文件。

4. 运行验证使用“首轮估算 + 稳定均值”。
   不只是外部候选，任何 `lb_*.py` 真实验证默认都至少跑到 `output.txt` 新增 2 条 `run=`。长流程投递命令使用 `python3 tfwr_orchestrator/tools/run_real_game_script.py --target-script lb_start --request-timeout <秒> --request-only`，不要让终端一直卡在等待 runner 结束；运行中状态查看使用 `python3 tfwr_orchestrator/tools/run_real_game_script.py --status-only --target-script lb_start --status-lines 80`。首轮未完成时只看 `progress_estimate` 里的游戏时间 / tick 判断是否值得继续等，不看现实耗时判断策略优劣；首轮完成后只看已完成轮均值。若最近两轮成绩差异不超过 `10%`，直接用当前均值判断方向；若超过 `10%`，继续运行直到最近两轮稳定。如果 `30s` 没有新增游戏输出和模组输出，按卡住或明显低效停止。不要因为外层墙钟还没到就继续等，也不要因为资源在 `item_snapshot` 里上涨就忽略没有完成轮的问题。`finished=false runs=... average=...` 是取消摘要，不是完成轮证据；完成轮只认 `output.txt` 中新增的 `[lb_xxx] run=... time=...`。

5. 失败结果要分清“脚本坏”和“策略弱”。
   入口不对、目标不对、缺最后 harvest、没有触发 leaderboard 结算，这些属于脚本适配问题，应修复后再测；修复后仍慢，才记录为策略失败。

6. 更快的候选必须做复盘。
   只记录成绩不够，必须在对应 `lb_xxx.md` 里写清楚为什么更快、它打破了当前哪条假设、之前的搜索空间哪里收窄错了、这条经验能否迁移到其他榜单。如果经验可迁移，应同时抽象到本 README 的共用注意事项。

7. 迁入真源后必须再验证一次。
   外部脚本在真实存档临时覆盖里跑通，只能证明候选有效；迁入 `references/leaderboard_scripts/lb_xxx.py` 并通过同步工具部署后，还要再次真实验证，确保真源版本和临时版本一致。

## `lb_xxx.md` 推荐模板

每个榜单 md 建议统一包含以下栏目：

1. 榜单目标
2. 当前基线
3. 通用注意事项下的榜单特化
4. 当前版本结论
5. 失败对照
6. 下一步优化方向
7. 候选策略方向（猜测 / 待验证）

其中“候选策略方向”必须满足：

- 显式标明“猜测 / 待验证”
- 和“已验证结论”分层记录，不能混写
- 每条都应说明：
  - 核心思路
  - 它试图解决的主瓶颈
  - 相比当前路线为什么可能更强
  - 最值得先验证的 1 到 2 个探针点

## `lb_*.py` 注释边界

`lb_*.py` 可以保留：

- 与实现强绑定、不贴着代码就难理解的少量说明
- 当前脚本版本对应的成绩摘要
- 关键魔法数字来源说明

`lb_*.py` 不应继续保留：

- 长篇版本演进史
- 成段优化思路
- 失败路线复盘
- 通用方法论
- 大段“当前建议 / 下一步方向”
