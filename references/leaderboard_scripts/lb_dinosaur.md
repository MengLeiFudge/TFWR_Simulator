# lb_dinosaur

## 榜单目标

- 目标资源：`Items.Bone`
- 当前脚本目标数量为 `33488928`
- 核心不是普通农业收益，而是恐龙帽状态下尾巴长度与结算倍率

## 结算机制说明

- 这题本质上就是经典贪吃蛇，只是落在 TFWR 的农场网格里。
- 关键机制可以直接概括成：
  - 戴上 `Dinosaur_Hat` 后，如果有足够仙人掌，会自动购买一个苹果并放在无人机脚下
  - 当无人机站在苹果上再次移动时，会吃掉苹果，尾巴增长一节
  - 如果还有足够仙人掌，就会尝试在随机空位生成下一颗苹果
  - 戴恐龙帽时不能穿越农场边界
  - 尾巴会填充无人机走过的地块；如果试图移动到尾巴上，`move()` 会失败
  - 但尾巴最后一节会在移动时移开，所以可以踩到“刚刚离开的尾尖”
  - 苹果上调用 `measure()` 会返回下一颗苹果的位置
- 反编译源码 `DinosaurHat#OnMove()` / `DinosaurHat#BoneCount()` 给出的关键事实是：
  - 初始 `move()` 成本是 `400 ticks`
  - 每吃一颗苹果，后续 `move()` 成本会减少 `3%`，向下取整
  - 卸下恐龙帽时，骨头收益是 `尾巴长度^2 * 科技倍率`
- 当前满级科技倍率是 `32`
- 在 `32x32` 农场里一共 `1024` 个格子
- 最终满盘状态下：
  - 头占 1 格
  - 尾巴最多占剩下的 `1023` 格
- 所以当前 leaderboard 目标值的来源非常明确：
  - `33488928 = 1023 * 1023 * 32`
- 这意味着当前恐龙榜不是“滚很多轮尾巴再结算”，而是一次到位问题：
  - 目标就是在一局里把尾巴吃到 `1023`
  - 然后卸帽一次性结算

## 当前基线

- 当前默认入口：`main6()`
- 当前路线：32x32 固定哈密顿回路，依靠“按安全回路持续吃苹果，尾巴长到 `1023` 后一次 cash-out”
- 2026-04-24 真实验证：`main6` 3 轮均值 `33:10.221`
- 证据来源：`lb_dinosaur.py` 顶部注释、`main6()`、以及 `quick_print("main6 done ...")`

## 通用注意事项下的榜单特化

- 这个榜单的主收益是“单局满尾巴平方结算”，不是高频 harvest
- 因为目标值刚好等于 `1023^2 * 32`，所以不存在“差不多够了就提前收”的空间
- 活得足够久、避免自撞、控制苹果获取路径，比普通移动微优化更重要
- 世界大小、路径覆盖率、是否能安全吃到远处苹果，是第一优先级变量
- 同时这又不是普通等权最短路：
  - 越早吃到苹果，后续 `move()` 越便宜
  - 所以早期苹果的时间价值比后期更高

## 当前版本结论

- `main1..main4`
  - 早期贪心 / 局部打分方案
  - 文件明确给出的结论是：死亡过早，bones 依赖多局累积，太慢
- `main5`
  - 两阶段贪心 + parity 限制路径
  - 已明确落后 #1 约 11 分钟
- `main6`
  - 固定哈密顿回路
  - 当前主线：不再赌局部最优，转而用完整覆盖路径换绝对安全
  - 在当前目标值下，这条线的正确性基础非常清楚：只要能安全吃满 `1023` 个苹果，就能一次结算达标
  - 2026-04-24 真实验证 3 轮均值 `33:10.221`

## 失败对照

- 早期“见苹果就追”的贪心类方案
  - 核心问题不是找不到苹果，而是活不到足够长
- `main5`
  - 两阶段相比纯贪心更稳，但仍不足以逼近榜前
- “不吃满也许更快”的阈值收割思路
  - 这条线当前应视为错误口径
  - 因为目标值就是 `1023^2 * 32`
  - 既然目标本身已经钉死在满尾巴，提前收就天然不可能达标

## 下一步优化方向

- 给 `main6` 补每轮苹果数/尾长日志
- 重点确认：
  - 固定回路里真正的时间大头是移动、找苹果，还是后期尾巴调度
  - 早期少走几步、尽早吃苹果，对总时间的复利收益到底有多大
- 优化目标应明确写成：
  - 不是寻找更早的收割阈值
  - 而是更快、更安全地吃满 `1023` 个苹果

## 候选策略方向（猜测 / 待验证）

### 方向 1：哈密顿主回路 + 受限安全捷径

- 核心思路：默认沿固定回路走，但当苹果落在局部安全窗口内时允许短切
- 主瓶颈：纯哈密顿回路安全，但吃苹果的平均等待可能偏高
- 可能更强的原因：如果只在可证明安全的小窗口做捷径，可能吃到一部分贪心收益而不重回早期自撞问题
- 优先探针：
  - 纯回路下苹果平均等待步数
  - 2x2、3x3 局部窗口内安全短切的成功率

### 方向 2：前期贪心增尾，过阈值后切回固定回路

- 核心思路：把 `main5` 的阶段思想保留，但切换阈值更早、更保守
- 主瓶颈：早期完全固定回路可能吃苹果偏慢，后期继续贪心又容易死
- 可能更强的原因：前期用有限贪心加速增尾，后期用回路保命，可能比纯任一侧更平衡
- 优先探针：
  - 不同尾长阈值下的死亡率
  - 切回回路后的苹果获取效率

### 方向 3：利用“越早吃苹果越便宜”的特性重排早期路径

- 核心思路：不是改变最终目标，而是让前几十颗苹果尽量更早被吃到，以便更早触发 `ops -= floor(ops * 0.03)` 的连锁降耗
- 主瓶颈：纯哈密顿回路虽然安全，但前期吃苹果的等待可能偏长
- 可能更强的原因：早期每少走一步，都可能通过更早降 `ops` 在后面继续放大收益
- 优先探针：
  - 前 50 / 100 个苹果的平均获取步数
  - 更激进的早期吃苹果策略对总时间的影响
