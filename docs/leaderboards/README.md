# 排行榜策略与研究记录

本目录保存30份同名榜单策略文档、共用研究方法及一份进度总表。当前可执行实现位于[scripts/leaderboard](../../scripts/leaderboard/README.md)，被替换版本和未采用候选位于[历史代码库](../../references/leaderboard_history/)。单榜结论写回对应`lb_xxx.md`，不再新建阶段、日期或验证批次文档。

## 排行榜状态汇报

用户询问排行榜时，回复与[进度总表](leaderboard_progress.md)统一使用七列，顺序固定：

| 排行榜 | 实机 | 模拟 | #1 | #3 | #10 | 改进方向 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 榜名及单／多机 | 账号最高时间（#排名） | 已有最好有效模拟 | 公开第一名时间（差距%） | 公开第三名时间（差距%） | 公开第十名时间（差距%） | 下一步具体机制或瓶颈 |

- #1、#3、#10取对应公开排名；不足3人或10人时，相关列显示末名时间、差距及排名，例如`9:10.000（+50.0%）（#8，末名）`，百分比按该末名时间计算。空榜或缺失数据写“未取得”。所有榜以#1为目标，#3、#10与前排分布用于判断可实现水平。
- “实机”只指当前账号在该公开榜上的历史最高记录，并附排名。本机最近完整统计、最好单轮、短筛和缓存估位另记，不能代填账号记录。确认无记录写“未上榜”，查询失败且无可用旧值写“未核实”。
- “模拟”取满7200游戏秒的**场均会话**时间（与公开榜完整统计同口径，用[会话工具](../../simulator/headless/session.py)跑），允许未采用实现；单seed单轮只作方向筛选，不填进这一列。逐轮明细、轮数与标准误存原始回执（`.codex/`），单榜页在下次改动该榜时同步本轮口径；未采纳候选写清与采纳版的差距。失败或未达成目标的轮使整场无效，不得当作完成时间；批量机制至少兑现一个完整周期。
- 基准时间取有效实机、有效模拟中较快者；仅有一种有效时间时用该值。#1、#3、#10时间后各附`(基准时间 / 该名次时间 - 1) × 100%`，保留一位小数与正负号，正数表示我们更慢，负数表示我们更快。例如基准150秒、#1为100秒，显示`1:40.000（+50.0%）`；基准50秒、#1为100秒，则显示`1:40.000（-50.0%）`。两种有效时间均缺失时只显示公开时间。排序、阶段目标及实机准入继续按相对#1的差距判断，2倍对应`+100.0%`。
- 时间显示为累计分钟、秒和毫秒，比例用原始精度计算。改进方向写机制、分工或主成本，不只写“继续优化”。
- 榜单事实、账号状态及各自查询时间归[公开缓存](../../references/leaderboards/leaderboard_cache.json)；逐榜来源、日期和刷新失败信息归[公开快照](../../references/leaderboards/status_snapshot.md)。离线重建保留原抓取时间，表格单元格不重复添加“历史缓存”；使用旧缓存时在来源说明其时效。

单榜研究只刷新该榜；用户查询全榜时刷新全部30榜，默认前100名。修改本地结果或方向后，更新`leaderboard_progress.json`并运行：

```bash
python3 game_control/tools/refresh_leaderboard_cache.py --script lb_maze
python3 game_control/tools/refresh_leaderboard_cache.py --offline
```

工具只生成进度总表与公开快照两份Markdown。参数和代理设置见[排行榜缓存](../../game_control/README.md#排行榜缓存)。阶段顺序见[三阶段计划](strategy_review.md#三阶段计划)。

## 共用打榜注意事项

### 策略选择与淘汰

每次开始一个榜、收到优化方向或结果不足以支持继续投入时，先回答“为什么做这个方向、还有哪些方向、预计收益和置信度如何”，将判断写入对应单榜页。拓宽方向须从最基础的前提出发大胆提出替代假设，先列出来，再核对机制与成本；现有脚本的流程、布局和分工不自动成为游戏限制。用户明确指定且机制可行的改动须完成最小候选与本地对照，不以收益小或仍需找路线为由跳过。

1. 先区分已由游戏源码／对照证实的规则、尚未验证的机制判断、仅为当前代码方便而采用的安排。会排除整类方向的硬限制必须附证据与适用场景；证据不足保留为待验证，不能写成确定事实继续沿用。
2. 从下表逐项提出替代前提，再按维护的状态、允许的变形和恢复条件区分算法。名称相似、用过同种数据结构或试过一个代表，都不能证明已经覆盖。

| 基础前提 | 必须主动比较的问题 |
| --- | --- |
| 世界和地形 | 必须clear重生吗，能否保留进度继续下探？必须当前地图大小吗，能否多个独立小任务？ |
| 布局与生产准备 | 必须种满吗，能否少种换短闭环？必须全部筛选／准备完才生产吗，能否先兑现已有产出？支撑能否全图静态共享？ |
| 机器分工 | 必须所有机器协作同一任务吗，能否各做独立任务？单机阶段的其他机器能否准备后续资源？ |
| 定位和信息 | 必须全扫吗，能否先勘探、少量采样或利用已有几何？需要重复测量吗，旧信息何时失效？ |
| 阶段与同步 | 必须沿用当前阶段顺序或实体信号屏障吗，能否用统一时钟、限制每档负载、增量推进或重叠成熟？ |
| 资源和结算 | 必须取得当前数量、买当前科技、跑当前批次吗？混合获取、副产物、按缺口收尾与提前投资能否降低总成本？ |

3. 核对替代前提。与已证实规则冲突立即淘汰并注明依据，不为已知不可能者编写探针；未知前提用最小、有预算的对照判断。机制不可行、实现错误、耗时过高分别记录。对可行方向先做闭式或近似预算，包含初始化、定位、供料、移动、成熟、同步和结算；标明距当前#1差距、收益置信度及依据、最小验证和停止条件，再选少量代表深入。
4. 每个已列方向记录“待验证／机制否定／已对照／已采用”及实际下一步；待验证者给出本轮要验证的代表或暂缓理由。写入“下一步”不算已尝试，检查时须能找到对应候选、报告或机制否定证据。较好时间仍超过2×#1时优先重列主机制，不在旧框架无界调参；用户指定细化当前算法时仍采用每个有效改善。
5. 失败只排除实际验证的前提、布局、路径、状态表示和调度组合。换前提或组合后重新算完整费用，不把单项负例扩展为整类方向无效，也不把独立提速相加。已证实更慢的相同组合不原样重试；尚未覆盖的组合不能标为已关闭。
6. 阶段无进展时复查上表、旧结论的证据和未验证方向，必要时读外部源码、依赖及策略演进记录，保存来源、版本、许可和已读范围。不能只按文件名或作者成绩判断算法，也不能等用户给出具体构造后才检查基础前提。策略稳定后再按实际费用做机械优化；选择依据或通用方法变化时立即更新正式文档，草稿只保留进行中状态和引用。

已核实的具体遗漏与纠正见[六类经验](github_strategy_research.md#从基础前提拓宽的经验)。

### 重置榜的科技路线计价

两项快速重置均以“从零到实际解锁排行榜的总时间”为唯一目标，先按资源速率比较科技路线，再写完整脚本。由最终付款倒推生产方式、真实API要求和最低资源，必要前置与可选投资分列；科技树UI父连线及普通Reset前缀不是地下Reset的必经链。现行脚本的订单与分段不限制规划范围。

1. 建立按时间排列的资源账，包含最终付款、必要解锁、可选升级、种子／勘探消耗、阶段库存和终点余额。`unlock`可不检查UI父项，但附加条件仍须满足。前期种植看随后数笔需求及种子周转，不能只满足当前一笔升级再重新筹下一笔。
2. 先检查改变后续全程速率的决策：首次供电、速度、各级伴生、机器数、地图和主作物产量。只要不依赖某项升级，供电就须与该升级交换顺序比较；不能把树／草增产默认当成向日葵的必要前置。在供电成本相同、A/B为可加速工作的粗算中，`A+B+C`与`C+(A+B)/2`直接比较，再扣新增供电筹资和耗电。天然成熟等待等不随动作翻倍的部分单列，不因此跳过第一轮粗算。
3. 每个可购买伴生等级都比较筹骨投资与之后草、树、胡萝卜、Weird等实际受益需求，包含何时购买和可提前支付的后续科技。一个Poly2负例不能成为整轮固定Poly1的依据；升高伴生后的生产率也必须用于重算其他投资，不能只在旧路线中插入一次购买。
4. 混合获取同时检查副产物和成熟等待重叠。记录联合净产量、科技、机器数和可用时点；按后续需求比例种植长周期作物，等待时在少量短周期格收草、补种或筹其他资源，比较全田巡回与局部短闭环。后续缺口扣实际副产物，删除生产也扣其副产物；不重复计算时间，不把末段库存倒用到前期。水肥自动积累、感染联产同样入账。
5. 粗算必须覆盖改变相互回报的组合。普通Reset至少列现行8机/C2/D4、16机/C3/D5及高阶伴生下的代表，注明购买时点；地下Reset按自己的终点选机器数、地图、采矿／作物等级。先用8→16机的可并行部分约减半、C2→C3的同量仙人掌生产约减半做低成本筛选，再校正派工、成熟和串行项。所有新增科技均按候选当时的新速率筹资，不能用旧速率算投资、用新速率算收益。迁入新的生产／筹金模块时，保留“只换模块、原机数与地图不变”的对照，再比较增机、扩田与购买时点；生产模块改变后须重算机数的回本，避免昂贵投资掩盖模块本身的收益。
6. 明显余量同时比较“少采省多少”和“提前／推迟投入升级省多少”，再比较组合。不为清零买无法回本的科技；整批零头、自动积累和有用副产物须说明。独立串行资源用`缺口 / 当前净速率`估算；混采使用联合约束，可并行阶段算依赖关键路径，另计切换。升级比较新增筹资与剩余需求的`Σ需求 × (1/旧速率 − 1/新速率)`，倍率只作用于实际受影响部分；计入耗电动作和缺水肥等待。
7. 写候选前留下少量路线的成本表：科技等级与购买时点、分段速率／倍率、剩余需求、新增投资、混采与等待重叠、预估总时间、主要不确定项、保留／排除理由。缺少组合写“未粗算”，不能写成已淘汰；没有这张表，不能声称完成了路线筛选。粗算的用途是快速暴露大收益组合，不要求先写完整脚本或跑模拟。
8. 对粗算保留的少量代表，用相同初始条件和预先选择的seed集配对模拟，记录科技、阶段库存和真实结算。新seed加入后按共同较大样本重比，不删失败seed报均值，不拼接阶段节省当整轮成绩。精确模拟负责检验粗算与实现，不能替代前面的策略枚举和计价。
9. 与榜前对照时先按双方都已获得的能力对齐，再算差距：取两边共有的里程碑（如向日葵已解锁、伴生1＋双机、伴生1＋四机、八机＋Mazes2），差距是这两点之间的时间，不是各自解锁时刻的差。对齐后先算可替代投资——同一批资源买 A 还是买 B，按各自的后续回报比，不能因为某一项解锁更早就把它当收益；也不把“提前拿到八机”的时刻直接当成整轮收益。
10. 最终从零筹资并实际付款，复查漏账和余额。所有路线仍远离榜首时重新检查资源来源、升级顺序与可用机制。两榜的当前账目、已覆盖范围和淘汰组合分别归[普通Reset](lb_fastest_reset.md)和[地下Reset](lb_fastest_underground_reset.md)；单项负例只排除所测等级、顺序和生产条件。

分析重置录屏时，阶段目标和升级时间之外，必须记录实际种植与移动：按地图阶段画格子布局，标出作物／留空位置、收补顺序、环绕方向、短闭环、回访时机及布局切换条件。先用连续相邻帧确认一段完整巡回，再写最小复现候选；只改科技顺序、沿用自己的生产路径，不能称为复现视频。画面已能确认的可行操作直接照做并本地比较，不要求先发明另一种算法；看不清的操作明确标注并补看，不能用旧脚本填补后宣称已经验证。

### 固定效率闭环

所有游戏脚本先满足[语法、正确性、效率与替换要求](../script-validation.md)。功能初版全科技，重置榜用原版初始条件。已有模型优先用[C#完整模拟器](../../simulator/headless/README.md)；简化动作模型不计完整解释器费用，不能代替完整执行证据。当前模型覆盖、误差和未覆盖部分以[验收记录](../../simulator/headless/validation.md)为准。

- 以当前#1反推核心预算：伴生有效收获周期与重抽／支撑、恐龙move/apple、仙人掌move/swap/measure、迷宫节点与宝藏路径；初始化、成熟、同步和结算均计入。
- 理论枚举先剪枝，探针保存在`.codex/`并设置规模、时间、动作上限及早停。预计超过60秒有进度，30秒无有效输出停止缩小输入。阶段日志用0t的`quick_print()`，`print()`约耗1游戏秒，参数计算仍计费。廉价写法见[解释器费用](interpreter_cost_notes.md)。
- 策略基线正确稳定后，按[母版与固定代码生成](interpreter_cost_notes.md#母版与固定代码生成)检查源码实际费用，生成少量有依据的变体并同条件择优；有效微小收益也采用。已接入者只手改母版及规则，配方与当前最好产物一起入Git，临时A/B/C及回执留`.codex/`。
- 有效改善先更新最快源码及单榜文档，组合后复验。存档覆盖另核对旧版、依赖、idle并备份；可用实际短程效率，不必等原目标完整结束，但批量机制须正常兑现。复制不授权游戏执行。
- 实机准入两条独立路径：用户明确授权该任务；或有效模拟≤2×当前#1且严格快于账号公开最高记录。运行前记录所用路径、源码版本、seed／窗口、预估、#1和账号记录来源与时间；自动路径缺少可比值不推定达标。规则覆盖短筛、迁入复验与包装入口。
- 获准后至少观察两轮，最近两轮差异>10%增加轮次，但**短样本只比快慢、不提交成绩**。游戏把成绩攒成一次完整统计：累计约7200游戏秒才结算，上传分数取该场全部轮次的均值，并要求本场结束时`finished=true`；因此两三轮的短样本即使每轮更快也不会改动公开记录，任何一轮失败还会让整场作废（2026-11-16 批量实机已实测确认）。确认要上传时用`--max-leaderboard-runs 0`跑完一场完整统计并给足客户端等待预算`--total-timeout`，以`full_statistics=true`的会话记为游戏打榜时间。短筛只认真实`run=`，取消摘要可能含未完成轮。
- 请求前部署；运行至同ID终态确认并回到idle期间冻结全部存档`.py`。运行中观察BepInEx日志，结束读`output.txt`并查Unity日志。连续30秒无模组日志停止诊断，快照心跳不证明产出。`--request-only`由调用者负责有界监测、停止和终态回收。
- 首轮资源线性增长才可外推。比较目标时间用`estimated_total_game_seconds`，剩余时间是`eta_game_seconds`，墙钟ETA仅安排占用。恐龙、仙人掌等未结算批量不能据零库存判卡住，重置榜按阶段判断。

### 耗时构成与机制上限

`--hot-spots`可按源码行和无人机拆分API tick与解释器tick。先用它判断脚本属于哪一类，再决定优化方向，不凭直觉换结构：

| 类别 | 观测判据（总tick／游戏秒） | 含义与可行手段 |
| --- | ---: | --- |
| 动作／解释器受限 | 约1.5e5～1.95e5 | 游戏时钟被动作与解释器追满，用时近似正比于总tick；减move／use_item／dig次数和解释器节点直接省时 |
| 机制等待受限 | 约6.1e3 | 脚本大多在等成熟、生长或动作计时，时钟按上限推进；压tick几乎无用，只能减少等待次数或提高单位时间产出 |
| 混合 | 3e4～1.5e5 | 两类都占一定比例，先分别核算有效动作与等待再选方向 |

2026-11-16 seed1单窗口实测分类：迷宫、干草、向日葵、稻米、竹子、胡萝卜、仙人掌、南瓜、蘑菇多机、石英矿在动作受限侧；恐龙、蘑菇单机、仙人掌单机、藏宝图、炸药单机、木头单机在机制等待侧；金字塔多机5.5e4、炸药多机3.4e4属混合。换结构后类别可能改变，优化前重新测。

### 共用策略原则

伴生倍率按真实`Growable.YieldFactor`及`5 << polyculture_level`计算，收益扣种子、重抽、支撑、移动和等待。初始化／失败重抽与成熟生产收获分开计数，支撑须在兑现时仍匹配。跨区域请求只能按真实收获倍率计产，不因接受时匹配就记高倍。已存在的成熟失配及其策略取舍在单榜页明确保留，新方案不能默认为正确。

无人机字典不共享；脚本API没有`get_drone_id`、`send`或`receive`。helper、物理邮箱或接力须证明写入归属、坐标传递、无阻塞和总吞吐；不能把反编译中未注册的方法体当作可用API。同机可以按支撑格与类型分批保持请求，多机还须处理唯一写者和真实种子资金。具体已失败布局查对应单榜表。

地图大小、环绕、生产密度与兑现结构需主动比较。区分200t动作和1t判断，少判断若带来更多误操作可能更慢。水、肥、支撑成熟、重种与规划均按完整收益收费。不得利用结算窗口重复收同一迷宫宝藏。

## 外部候选 `.py` 评估流程

先读入口、依赖、目标和许可，记录版本及已读范围；入口错误、缺收获或目标不符先适配，再判断策略。外部依赖迁入仓库实现，不能在真实存档新增依赖文件。打榜适配已有`lb_xxx`／`lb_start`，探针适配已有`test.py`。

用本地语法、正确性和完整费用对照筛选，再按上述实机准入运行。更快候选须解释打破了哪个假设，并在迁入源码后核对执行副本；新版本正式成绩取迁入复验，作者自述成绩不算本机实测。来源汇总见[GitHub](github_strategy_research.md)和[B站](bilibili_strategy_research.md)。

## `lb_xxx.md` 推荐模板

每份单榜文档固定四节，数值和机制结论直接保存在正文，原始轨迹、长哈希及批次回执留`.codex/`，不新建过程MD／JSON。

1. **当前策略与成绩**：目标和对应脚本、当前分工／状态／同步、主瓶颈；账号最高、有效模拟及本版本完整统计分开说明，注明日期、版本和模拟口径。
2. **淘汰与未采用方案**：表格列方向、实际表现、失败原因及适用范围、归档代码。机制判定与仅预算项注明未写代码，失败不扩大为整个算法类别不可能。
3. **历史正式版本演进**：按日期列核心变化、实机／模拟时间及归档文件；旧版合集中的函数可注明原入口。未注明成绩类别的旧注记不能升级为正式实机。
4. **下一步优化方向**：保留1～3个尚开放方向，写机制、收益依据、置信度、最小验证和停止条件；已关闭方向移入淘汰表。

| 时间名称 | 取值与最小证据 |
| --- | --- |
| 本地模拟预估时间 | 同脚本、同场景完整结果或实际窗口外推；记录模型、源码版本、seed、实际进度、方法和未覆盖部分 |
| 短时打榜测试时间 | 筛选请求中真实完成`run=`的均值；记录请求、完成轮、范围和停止原因 |
| 游戏打榜时间 | 一次正常完成官方完整统计；记录请求、完成轮、最终值、部署版本和双日志 |

各项附日期及游戏／模型版本；官方最终值和逐轮重算均值如有舍入差保留各自来源。不同seed均值差不等于同seed模型误差。账号最高仍独立取公开记录。

历史代码归`references/leaderboard_history/<lb_xxx>/`，旧正式版本按日期、版本号、成绩及提交号命名，候选按日期、方向及有效时间命名。失败或局部窗口的档名时间不能当整轮成绩，代码、来源路径和提交映射维护在`manifest.json`。档案不参与类型检查、部署或游戏导入。

## `lb_*.py` 注释边界

当前可执行脚本固定：首行`from __builtins__ import *`，随后完整轮时间注释，第一个函数与文件同名，辅助函数随后，末尾`if __name__ == "__main__":`调用同名入口。可执行目录只保留当前确认最快实现；已接入生成者在成绩注释后标明母版和配方，只修改母版及规则，不能手改生成物。母版、生成器和配方按[存放约定](interpreter_cost_notes.md#文件存放与人工修改)入库；版本、失败和接近候选移入对应文档及历史代码库。

仓库`lb_start.py`是入口／历史完整复跑索引，右侧列在当前版本完整统计结束后更新；存档同名文件是部署生成物。无需`lb_start.md`，短筛、模型或账号历史最高不替代该版本完整复跑。
