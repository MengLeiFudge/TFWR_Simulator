# Leaderboard Scripts

这个目录承载两类长期资料：

- `lb_*.py`
  - 具体榜单脚本真源
  - 只保留必要实现说明、关键魔法数字来源、当前成绩摘要

- `lb_*.md`
  - 具体榜单的策略文档
  - 承接目标、基线、版本结论、失败对照、下一步方向、候选策略

`lb_start.py` 例外：

- 它是部署时生成的入口脚本
- 不属于具体榜单的长期策略真源
- 不需要也不应配套 `lb_start.md`

## 共用打榜注意事项

以下内容承接并改写自历史提交 `00f01b30` 中 `AGENTS.md` 的 `## 第二阶段优化器关注点`，但语境已经切换到当前真实游戏 oracle workflow。

1. 先研究决定 leaderboard 成绩的收益结构，不先做语法级微调。
   如果一个榜单的主收益来自 companion、连通块、全图并行、或某个特殊结算倍率，就应先围绕这个主收益设计路线，而不是先卷局部 tick 小优化。

2. 伴生、高倍率机制、版图布局、路径和回访节奏通常优先于局部实现细节。
   对依赖 companion 的榜单，没吃到 companion 往往就接近没有有效收益；对不靠 companion 的榜单，应优先围绕真正的结算机制做设计。

3. 世界大小和版图布局通常是第一优先级决策变量。
   默认世界大小不一定是最优解；应主动评估小图降移动成本、大图拉高并行吞吐、穿边、跨边界 companion、块划分等收益。

4. 必须明确区分 `200t` 操作和 `1t` 判断的成本模型。
   默认优先“多判断、少误操作”。只有当主流程已经稳定、判断不再明显减少昂贵动作时，才考虑进一步削减这些廉价判断。

5. 水、肥、重种、reroll、support 改写都要按收益 / tick 成本评估。
   这些动作不能因为“可能有帮助”就默认加入；应明确它们试图解决什么瓶颈，以及实际是否值得。

6. 不同 leaderboard 的目标函数和瓶颈不同，不能硬套统一模板。
   `fastest_reset`、`maze`、`pumpkins`、`sunflowers`、`wood` 的最优策略结构很可能完全不同；先识别主瓶颈，再决定搜索空间。

7. 验证节奏必须分层。
   默认先做单次验证，确认方向没有明显慢几十秒；接近基线后再做多 seed 对比；只有差距已经足够小，才值得跑更长流程看均值。
   请求启动后必须持续检查游戏 `output.txt`：打榜脚本每完成一轮必定新增一行输出，如果连续 `30s` 没有新增输出，应停止本次请求并判定该候选卡住或明显低效。游戏内是否变快必须优先看脚本输出的 `time=`、阶段切换日志、资源增量和 leaderboard summary；如果多无人机导致实际加速倍率低于 `200x`，这是验证环境现象，不能直接判定策略变慢。
   评估外部候选或新策略时，`run_real_game_script.py` / `real_game_runner.py` 默认跑到 2 条新增 `run=` 输出就停止；两轮已经能判断明显优劣时，不要继续等待更多轮。只有要刷完整官方统计或专门观察长尾均值时，才显式传 `--max-leaderboard-runs 0`。
   `simulate()` / `leaderboard_run()` 的最后一个参数是模拟速度上限，不是保证倍率；当参数设得很大，例如 `10000`，真实速度会受电脑性能和脚本计算量限制。高计算型脚本出现现实 `1s` 只推进游戏内 `10s` 这类情况是正常现象，不能用外层墙钟直接比较策略。

8. 长流程验证应允许动态停表。
   脚本应主动打印足够细的阶段日志，例如阶段名、`time=`、关键资源、无人机数、目标值。代理验证时可以根据这些日志判断方向已经明显无效、已经达到目标、或需要切换探针，并提前停止；不得机械等待外层 `1min`。如果提前停止，必须把停止依据写成“游戏内阶段时间 / 资源进度 / output stall”，不要写成单纯墙钟耗时。

9. 真实游戏结果优先于仓库内推断。
   `output.txt` 是最高优先级运行进度证据；`LogOutput.log` 是第二优先级，模组请求运行中应每秒输出 `item_snapshot` 展示当前所有物品数量；`state.json` 只在开始前和终止后确认状态。如果 `output.txt`、`LogOutput.log`、真实存档行为与当前脚本推断冲突，应优先修认知，而不是硬保留旧结论。

10. 所有魔法数字都必须注明来源。
   来源至少应指向以下之一：
   - 真实游戏常量
   - 反编译源码
   - probe 实测结果
   - leaderboard 基线数据
   - 明确的成熟 / 回访节拍推导

11. 失败路线也要长期留档。
    已经验证明显偏慢、冲突过高、收益不足的方向，应写进 `lb_xxx.md` 的“失败对照”，避免后续重复试错。

## `lb_xxx.md` 推荐模板

每个榜单 md 建议统一包含以下栏目：

1. 榜单目标
2. 当前基线
3. 通用注意事项下的榜单特化
4. 当前版本结论
5. 失败对照
6. 下一步优化方向
7. 候选策略方向（猜测 / 待验证）

其中“候选策略方向”必须满足：

- 显式标明“猜测 / 待验证”
- 和“已验证结论”分层记录，不能混写
- 每条都应说明：
  - 核心思路
  - 它试图解决的主瓶颈
  - 相比当前路线为什么可能更强
  - 最值得先验证的 1 到 2 个探针点

## `lb_*.py` 注释边界

`lb_*.py` 可以保留：

- 与实现强绑定、不贴着代码就难理解的少量说明
- 当前脚本版本对应的成绩摘要
- 关键魔法数字来源说明

`lb_*.py` 不应继续保留：

- 长篇版本演进史
- 成段优化思路
- 失败路线复盘
- 通用方法论
- 大段“当前建议 / 下一步方向”
