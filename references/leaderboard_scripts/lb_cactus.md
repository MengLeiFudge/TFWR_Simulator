# lb_cactus

## 榜单目标

- 目标资源：`Items.Cactus`
- 当前脚本按多无人机路线设计，目标数量为 `33554432`
- 你补充的当前关键事实：
  - `32 * 32 = 1024`
  - 满 `32x32` 仙人掌盘收割一次的收益是 `1024 * 1024 * 32 = 33554432`
- 这意味着当前榜单目标值正好等于“满 `32x32` 合法盘面收割一次”
- 核心机制不是 companion，而是把整图 cactus 调整到可一次性按“合法有序连通块”结算的状态

## 结算机制说明

- 这里的结论来自反编译源码：
  - `Cactus#Harvest()` 会调用 `Pop(...)`
  - `Cactus#CountSorted(...)` 会统计当前可结算的 cactus 数量
  - `Cactus#GetDrops(...)` 会把这个数量换算成掉落
  - `Growable#YieldFactor` 决定基础倍率
- 要看懂 cactus 为什么是 `地块数 * 地块数 * 32`，关键是先分清楚“到底哪些仙人掌会被算进去”。
- 游戏不是简单按“连在一起的 cactus 数量”结算。
- `CountSorted(...)` 的逻辑是：
  - 当前 cactus 自己必须先满足 `IsSorted()`
  - 之后只继续统计那些“已经成熟、自己也满足 `IsSorted()`、并且和当前 cactus 连通”的仙人掌
- 所以真正参与计数的不是“同簇数量”，而是“合法有序连通块”的大小。
- 这也是为什么“只追求同簇”是错误说法；同簇但没排好序，计数照样上不去。
- `GetDrops(int numPopped, int numWeird)` 的核心计算是：
  - `num = YieldFactor * numPopped`
  - `n = numPopped * num - weird_penalty`
- 在当前 leaderboard 目标里，我们默认追求 `numWeird = 0`，所以可以直接化简成：
  - `掉落 = numPopped * numPopped * YieldFactor`
- `Growable#YieldFactor` 在当前 cactus leaderboard 下等于 `32`
- 所以只要合法有序连通块大小是 `N`，收益就是：
  - `N * N * 32`
- 套回本榜单：
  - 满 `32x32` 的合法有序连通块大小是 `1024`
  - 一次收割收益就是 `1024 * 1024 * 32 = 33554432`
- 这也解释了为什么当前多机 cactus 的正确目标是：
  - 尽快做出一次满 `32x32` 合法盘面
  - 然后只收这一次

## 通用注意事项下的榜单特化

- 这个榜单的主收益来自“大簇一次性结算”，不是频繁回访单格
- 但这里的“大簇”必须理解成“成熟且 `IsSorted()` 的合法有序连通块”，不是单纯连在一起
- 世界大小、排序方式、最终收割时机比局部移动细节更重要
- 这里几乎没有 companion 维度，优先关注“形成整盘可收割顺序状态的总动作成本”
- 既然目标值正好等于满 `32x32` 收一次，那么这个榜单本质上是“尽快做出一次完整可收盘面”
- 因此它不是长期平均产量优化问题，而是一次性构盘问题
- 按你给出的公式反推，`32x32` 是唯一正确的大图路线；分片路线不成立

## 失败对照

- gamesave 已废弃的 `main2`
  - 直接全图 reroll 到 `variant=9` 的思路在真实打法上不可行
  - 根据你的确认，并不是每个格子都一定会出现 `0-9` 的所有数字
  - 这意味着即使重置极多次，也可能因为某个格子始终出不来 `9` 而卡死
  - 这条线不应再当作候选优化方向

- 分片路线
  - `16 * 16 = 256`
  - 单个 `16x16` 区域一次收割收益是 `256 * 256 * 32 = 2097152`
  - 需要整整 `16` 个 `16x16` 才等价于一次 `32x32`
  - 这说明分片不是捷径，而只是把唯一目标拆散后再重复做 16 次；在当前榜单上不可能优于一次完整 `32x32`
- 种植时顺手消一个横向逆序

### 方向 1：在行排序时顺手做列方向的预排序

- 核心思路：当前主线已经要逐行移动并比较相邻 cactus，高概率可以利用 `measure(direction)` 在行排序过程中顺手收集列方向信息，提前做一部分列整理
- 主瓶颈：当前 `main1` 的行排序和列排序是明显分开的，列排序是额外整轮成本
- 可能更强的原因：如果横向扫描时就能顺手完成部分纵向交换，独立列排序的轮数可能显著下降
- 优先探针：
  - 行排序阶段里，额外加入纵向判断后能减少多少后续列交换
  - 融合后总移动步数和总 `swap()` 次数是否下降
- 当前状态：2026-06-09 离线筛选已排除“排序后单独纵向 pass”和“行排序路径内直接 South 比较”；后续只有能证明不破坏最终合法性、且不额外扫完整行的融合结构才重开。
  - 2026-06-09 追加筛选已排除行列交替 relax：合法但总动作明显高于当前 rows_then_cols。

### 方向 2：种植阶段顺手交换，尽量少留后账给排序阶段

- 核心思路：既然种植阶段本来就要逐格访问，那么在新 cactus 落地时就顺手检查并交换一部分明显逆序的邻格
- 主瓶颈：当前很多交换动作是在“全部种完以后”单独再做的
- 可能更强的原因：能边种边排一点，就少一部分独立排序轮次；能少一步算一步
- 优先探针：
  - 种植阶段可以安全做掉多少交换
  - 提前交换后，后续纯排序阶段的边界收缩速度是否更快

### 方向 3：把行排序与列排序做成真正的双向融合流程

- 核心思路：不是“先把所有行排好，再单独列排”，而是在每一轮扫描中同时推进横纵两个方向的有序化
- 主瓶颈：当前主线的列排序仍然像附加的第二阶段成本
- 可能更强的原因：既然唯一目标是尽快完成一次满盘合法收割，那么任何能减少独立排序轮次的融合流程都有直接收益
- 优先探针：
  - 同一轮扫描里同时做横纵比较后，剩余未有序区域收缩速度是否更快
  - 融合流程是否会引入额外移动，导致交换节省被抵消
- 当前状态：2026-06-09 `cactus_fusion_screen.py` 已证明普通“行列交替 relax”不是可实机方向；它合法但测量 / 移动总量更高。后续只有能减少完整扫线次数的融合结构才重开。

### 方向 4：真正的 pair-worker 排序网络

- 核心思路：请求 `320` 证明“单机顺序奇偶排序”无效，但没有证明“多无人机同一行内并行比较”无效。
- 主瓶颈：当前每行只有 1 台无人机，奇偶相邻对仍然顺序执行。
- 可能更强的原因：如果把 32 台无人机集中到少数行 / 列上同时处理相邻对，才可能兑现排序网络的并行收益。
- 优先探针：
  - 先只对 1 行用 16 台无人机做一轮奇偶 pair compare，确认 `swap()` 并发是否稳定
  - 再比较“少数行高并行排序 + 分批处理所有行”是否能抵消无人机重定位成本
