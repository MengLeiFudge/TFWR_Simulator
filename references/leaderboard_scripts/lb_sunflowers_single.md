# lb_sunflowers_single

## 榜单目标

- 目标资源：`Items.Power`
- 单机路线
- 当前脚本默认目标数量为 `10000`

## 收益机制说明

- 向日葵的新花瓣数来自独立随机：
  - 反编译源码 `Sunflower#OnRestart()` 明确是 `randomSunflower.Next(7, 16)`
  - 也就是每次新种都独立落在 `7..15`
- 因此以下想法是错误的：
  - “现在低点数很多，所以接下来高点数概率会变高”
  - 当前已有的向日葵，不会影响新种向日葵的点数分布
- 倍率规则同样非常明确：
  - 被 harvest 的那株必须等于当前全场向日葵里的最大花瓣值
  - 且场上向日葵总数至少有 `10`
  - 满足时这次 harvest 才能 `x8`
- 所以向日葵的正确理解不是“固定收某个值”，而是“始终尽量收当前最大值”
- 单向日葵之所以相对好做，是因为：
  - 只有一个无人机
  - 当前全场最大值可以直接由它自己掌握
  - 不存在多无人机通信成本

## 当前基线

- 当前默认入口：`main2()`
- 当前路线：仿照多向日葵 `main4()` 的高吞吐思路，6x6 常驻向日葵，蛇形相邻移动，成熟就收、立刻重种，有水库存才补水；不再为严格最大花瓣付出高额等待和 `move_to()` 管理成本。
- 当前真实验证成绩：
  - `request_id=240`：`19:19.531` / `20:44.492`，两轮均值 `20:02.011`
  - `request_id=242`：真源同步后新增两轮 `21:15.898` / `22:32.812`，新增两轮均值约 `21:54.355`

  - `request_id=608`：2026-05-30 当前版本复跑 `10:35.599` / `10:19.684`，稳定均值 `10:27.642`；后续 `finished=false` 取消摘要不作为成绩
- 对比旧默认：
  - 旧 `main1` 5x5 路线同步后 `request_id=241` 首轮 `79:48.699`，明显慢于外部 6x6 路线
  - 外部 6x6 分桶路线约 `20:02.011`，说明单机这里“更精准地等最大花瓣”不如“更快重种刷新”

  - 内联 `move_utils.move_to()`，避免向真实存档新增依赖文件
  - 同步工具对 `lb_sunflowers_single` 生成 `lb_start.py` 时使用外部入口验证过的 `1000` 模拟速度

## 通用注意事项下的榜单特化

- 单机向日葵更像“用最少的错误 harvest 换到最多的高倍率”
- 这里的关键不是格子越多越好，而是：
  - 最大花瓣识别是否准确
  - 场上是否维持了足够的成熟支撑
  - 收尾阈值是否合理
- 单机不像多机那样难在通信，它的难点主要只是“当前最大值的切换时机”

- `main`

  - 核心思路是扩大到 6x6，并把一整轮新种的花瓣值分桶，优先收高花瓣成熟株
  - 真实两轮均值 `20:02.011`
  - 真源同步后请求 `242` 的新增两轮约 `21:54.355`，仍显著优于旧 5x5 路线
- `main2`
  - 当前默认路线
  - 迁移多向日葵接近 #1 的核心经验：少做全局最大值管理，优先提高成熟收割和重种频率
  - 第一版 `move_to()` 盲收 6x6：请求 `310` `12` 轮均值 `10:51.361`
  - 当前直走蛇形 6x6：请求 `315` `12` 轮均值 `10:23.160`
  - 2026-05-30 当前版本复跑请求 `608`：两轮稳定均值 `10:27.642`
  - 结论：单机仍吃不到多机 32x32 的规模优势，但高吞吐路线已把旧分桶基线缩短约一半
- 旧 `main1`
  - 旧默认 5x5 常驻路线
  - 同步验证首轮 `79:48.699`
  - 方向上“收当前最大值”没有错，但 5x5 小图 + 高频 sweep 管理成本太高，实际远慢于外部 6x6 分桶

## 失败对照

- 草稿里提过“单主位轮转”，文件顶已经明确认为它没有必要
- 也就是说，把向日葵做成单核心路线，当前默认视为不如满图持有
- “已有低点数会推高新种高点数概率”的思路
  - 这条线同样是错误口径
  - 因为新种花瓣数是独立随机 `7..15`
- 旧 5x5 常驻 sweep 路线
  - 2026-04-25 真实验证 `request_id=241` 首轮 `79:48.699`
  - 失败原因：虽然每次都尝试收当前最大花瓣，但反复全图 sweep 的管理成本远高于直接按分桶收割一批高花瓣成熟株
- 严格最大花瓣常驻计数路线：
  - 请求 `309` 两轮均值 `80:07.089`
  - 失败原因：虽然理论上避免错误 harvest，但当前最大花瓣成熟得太稀疏，收割密度崩掉
- 高花瓣阈值路线：
  - 请求 `312` 首轮 `174:57.031`
  - 失败原因：阈值切换后大量成熟低花瓣被跳过，资源速率低于盲收
- 宽松阈值混合路线：
  - 请求 `319` 在 6x6 直走蛇形上记录每轮最大花瓣，并按 `max_seen - 3` 收割，连续空扫再回退盲收
  - 新增有效轮约 `27:58.437` / `27:47.695`，明显慢于当前盲收基线 `10:23.160`
  - 失败原因：即使阈值已经很宽松，仍会跳过大量成熟低花瓣；单机向日葵的核心瓶颈是收割密度，不是少量提高高花瓣命中率
  - 处理：失败实现已从 `.py` 删除，仅保留结论
- 5x5 分桶排序路线：
  - 请求 `402` 两轮结果：`64:14.335` / `63:37.383`，均值 `63:55.859`
  - 失败原因：虽然按记录花瓣优先收当前最高值，但单机频繁 `move_to()` 和等待最高花瓣成熟，使收割密度远低于 6x6 直走盲收
  - 处理：失败实现已从 `.py` 删除，存档入口已同步回稳定 `main2()`
- 盲收地图尺寸对照：
  - 8x8 请求 `311` `11` 轮均值 `11:16.410`
  - 7x7 请求 `313` 运行中均值约 `11:04`，慢于 6x6
  - 5x5 请求 `316` `10` 轮均值 `13:13.529`
  - 结论：单机向日葵当前最佳尺寸是 6x6；8x8 虽然格子更多，但单机移动与循环成本更高
- 降低补水阈值到 `0.35`：
  - 2026-05-02 请求 `473`：runner 输出 `reached stable leaderboard runs 6 avg=10:29.245`。
  - 改法：`water_main2_if_available()` 从 `get_water() < 0.425` 改成 `get_water() < 0.35`，库存保护不变。
  - 有效轮包括 `10:24.273`、`10:34.945`、`10:24.062`、`10:28.799`、`10:29.492`、`10:33.899`。
  - 取消摘要 `finished=false runs=9 average=9:47.338` 不作为刷新成绩。
  - 结论：没有刷新；少补水会拉长成熟等待，代码已恢复 `0.425`。
- 提高补水阈值到 `0.50`：
  - 2026-05-02 请求 `486`：完整结束 `finished=true runs=12 average=10:33.509`。
  - 改法：`water_main2_if_available()` 从 `get_water() < 0.425` 改成 `get_water() < 0.50`，库存保护不变。
  - 有效轮包括 `10:23.873`、`10:37.299`、`10:31.757`、`10:34.880`、`10:34.899`、`10:29.799`、`10:33.299`、`10:33.398`。
  - 结论：明显慢于当前 `0.425` 基线 `10:23.160`；多补水没有压低总时间，代码已恢复 `0.425`。
- `main2` progress 日志阈值 `2000 Power`：
  - 2026-05-02 请求 `502`：完整结束 `finished=true runs=12 average=10:27.853`。
  - 改法：把 `main2()` 中 progress 输出阈值从 `last_log_power + 1000` 提高到 `+ 2000`，不改变 6x6 盲收、蛇形路径、补水阈值、库存保护和默认入口。
  - 有效轮包括 `10:25.499`、`10:42.070`、`10:04.450`、`10:27.656`、`10:25.663`、`10:35.273`、`10:21.249`、`10:43.867`、`10:20.937`、`10:26.249`、`10:27.882`。
  - 结论：没有刷新；减少 progress 输出没有降低完整均值，代码已恢复 `1000 Power` 日志阈值。
- 补水库存保护放宽到 `>0`：
  - 2026-06-09 请求 `704`：两轮稳定均值 `10:31.241`，有效轮为 `10:33.614` / `10:28.867`。
  - 改法：`water_if_available()` 从 `num_items(Items.Water) > SINGLE_FIELD_SIZE` 放宽到 `>0`，不改变 `0.425` 补水阈值、6x6 盲收和蛇形路径。
  - 结论：没有刷新，慢于当前复跑 `10:27.642`，也慢于历史 6x6 蛇形基线 `10:23.160`；单机虽然没有并发抢水告警，但更激进地耗尽尾部水库存没有净收益，代码已恢复 `> SINGLE_FIELD_SIZE`。
- 错收后等待当前最大花瓣清错误标记：
  - 机制前提：反编译 `Sunflower#Harvest()` 显示，上一株收错后，即使当前株原本等于全场最大花瓣，也会被强制不给 boost；只有一次“原本应 boost 的收割”能清掉错误标记。
  - 改法：6x6 蛇形路径不变；初始化和重种后记录每格花瓣值并维护计数。若上一株判断为错收，则后续成熟低花瓣先跳过，只等当前全场最大花瓣来清掉错误标记；若上一株未错，则仍允许盲收当前成熟株。
  - 请求 `705` 两轮有效成绩 `50:45.664` / `50:12.999`，稳定均值 `50:29.332`，明显慢于当前 `10:27.642` 量级。
  - 诊断日志显示第一轮 `skip=68010`、第二轮 `skip=67304`；跳过低花瓣造成的收割密度损失远大于减少错误链的收益。
  - 结论：不保留；单机向日葵不能通过“错收后等最大花瓣清标记”推进。后续仍应避免跳过大量成熟株，除非候选能证明几乎不降低成熟收割密度。

## 下一步优化方向

- 当前 6x6 直走盲收已是本轮最佳；请求 `319` 证明 `max-3` 也会严重牺牲收割密度，下一步不应再做阈值跳过类路线
- 已验证补水阈值 `0.35` 和 `0.50` 都没有刷新，默认保留 `0.425`。
- 已验证补水库存保护放宽到 `>0` 没有刷新，默认保留 `> SINGLE_FIELD_SIZE`。
- 已验证 `main2` progress 日志阈值 `2000 Power` 没有刷新，默认保留 `1000 Power`。
- 已验证错收后等待当前最大花瓣清错误标记会把成绩拖到 `50min+`；后续不要为了清错误标记跳过大量成熟低花瓣。
- 可继续补探针确认：
  - 是否能在“不跳过当前成熟株”的前提下，只用邻格局部偏好提高花瓣收益
  - 是否能减少 6x6 蛇形扫图的边界回绕成本
  - 是否只在前 1~2 轮使用花瓣筛选，之后切回盲收
  - 是否能减少 `get_water()` 调用而不显著降低成熟速度
- 当前不需要像多机那样先解决通信问题

## 候选策略方向（猜测 / 待验证）

### 方向 1：保留满图，严格按当前最大值分阶段收

- 核心思路：沿用外部 6x6 分桶路线，不预设“永远等 15”，而是按当前批次从高花瓣向低花瓣收
- 主瓶颈：最大值从 `15` 切到 `14`、`13` 的时机如果掌握不好，仍会空等
- 可能更强的原因：外部脚本已经证明“分桶后顺序收”远强于旧 sweep 路线
- 优先探针：
  - 每个花瓣阶段持续多久
  - 切值后单位时间 power 是否提高

### 方向 2：末段再放宽到 max-1，而不是全程只盯绝对最大

- 核心思路：前中段严格收当前最大值，末段为了避免久等再放宽到次大值
- 主瓶颈：终盘如果仍死等最大值，可能会空耗时间
- 可能更强的原因：单机能精确知道何时该从“严格最大”切到“次大也收”
- 优先探针：
  - 终盘阶段等待时间占比
  - 放宽到 `max-1` 后的净收益变化

### 方向 3：保留满图，但降低不必要的测量 / 管理开销

- 核心思路：单机没有通信问题，优化点更多在管理成本，比如什么时候测量、什么时候刷新记录
- 主瓶颈：管理动作虽然便宜，但总量也可能不少
- 可能更强的原因：在方向已经对的前提下，单机更可能靠这些细节抠出最后几秒
- 优先探针：
  - 每轮 `measure()` 次数
  - 降低管理频率后是否会导致明显错误 harvest
