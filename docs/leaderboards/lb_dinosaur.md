## 下一步优化方向

- 后续短切必须记录真实身体顺序。走过捷径后，身体的回路编号有空洞，不能用 `tail = head - length` 代替真实尾位置；苹果也可能出现在这些空洞中。局部不撞身不能证明最终能填满。
- 递归直出需证明直出路径、父区域恢复和未来目标均可达；所提 `id-(x+y) >= id-cnt` 只化为 `cnt >= x+y`，没有编码实际身体占格，不能直接作为安全上界。先用真实身体轨迹核对一条可恢复的退出代表，再写候选，不盲改判断。
- 外部检索按状态表示、允许变形和恢复条件区分算法；本轮只否定上述两个具体实现，未否定可恢复区域短切这一类方向。原始回执及重建器在 `.codex/five-structures-20261115/`，所有候选每例15墙钟秒，不放宽预算。
- 2026-11-16 `--hot-spots`：≈6.1e3 tick／游戏秒，属机制等待受限；满盘骨量`(格子数-1)²×2^(dinosaurs-1)`＝33,488,928，690秒吃1023个苹果约每果0.67秒，主要等苹果而不是算力，公开#1的0.29秒／果说明取果节奏更密。下一步先量同窗口的平均可吃苹果数与等待占比，再决定改路线还是改选果顺序。
- 同日用7200游戏秒场均口径（`simulator/headless/session.py`）跑 seed1-6：五轮 684.1/704.0/686.9/722.8/696.7 游戏秒，seed3 到脚本内 1200秒截止仍只有部分骨量（`stop_reason=finished` 但未达标），按公开榜规则整场作废；已达成轮均分 11:38.912。也就是说这个榜在2小时口径下约1/6轮会作废，多轮会话多半无效——**先修稳健性再谈提速**，与实机三次两次作废一致。
- 同日按反编译源码定下机制边界：`Dinosaur.OnMove` 返回的 `ops` 是 int，初始 400，每吃一个苹果 `ops -= floor(ops×0.03)`，跌到 33 后 `floor` 为 0 就不再降，所以移动单价下限就是 33t；种子1前150秒实测12,022次移动、911,276 tick，约75.8t／次，说明路费已接近该下限、不是主要抓手。苹果下一个落点由 `TryChooseTarget` 从“同深度内未被恐龙／苹果占据的空格”里均匀随机取（`randomSnake.Next`），空格数＝1024−蛇长；一个完整周期要吃1023个苹果，同窗口实测每果约13.4次移动，而均匀随机落点的几何均值本就在14～16次上下，所以随机追果已接近该机制均值。公开#1的0.29秒／果（约5.7次移动／果）低于均匀随机均值，不符合直接追果，优先怀疑重放 `randomSnake` 预测落点；在证实该路径前不再投入追果路线与短切优化。
