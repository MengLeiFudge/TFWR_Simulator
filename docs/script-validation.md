# 游戏脚本的模拟与替换准入

任何准备在真实游戏中执行的脚本，必须先用本地模拟器验证游戏语法、正确性和效率。覆盖真实存档已有的对应文件，还必须证明效率严格高于该文件的当前版本。模拟前先做[游戏语言静态检查](../simulator/local_simulator/syntax-validation.md)；不符合游戏语法的旧模型产量不能用作放行依据。编译、LSP及成熟排行榜来源只能作为补充证据。

## 默认条件与来源

功能脚本和普通资源排行榜脚本均以科技全解为前提。Fastest Reset类排行榜按其对应重置初始科技、库存和胜利条件运行。初版不加入低科技回退、科技升级规划或兼容分支；只有用户另行提出时才扩展。

优先使用用户已有的成熟功能脚本。没有对应功能实现时，先从仓库多机排行榜脚本迁入已验证算法，保留并行方式、布局、热路径、关键参数和来源许可，只做持续入口及普通游戏所必需的适配。重新设计必须先有机制理由和可比较的收益证据。水、化肥由游戏自动获取，不为它们设置生产脚本。

## 同条件对照

1. 冻结当前存档对应文件、全部依赖、候选及原算法来源，记录路径、SHA256和版本。用户已移出存档保存的原功能脚本仍可作为指定基线，必须记录它与当前存档版本的关系。
2. 固定同一套科技、地图、初始库存、随机seed和计时边界。全科技应明确使用包含DLC的配置；正式排行榜按自己的场景保留规则限制。普通地形与排行榜专用地形不能混作同一场景。
3. 连续产出使用“目标库存净增长 ÷ 实际经过的游戏秒”衡量效率，初步采样可给30秒现实计算预算；预算到了就报告实际游戏时间、净增长与增长率，不为凑固定游戏时长放宽预算。例如30秒现实计算推进100游戏秒、净增1e8，观测效率即1e6/游戏秒。600游戏秒可作为统一展示窗口，但不是准入的硬要求，短段样本不能填写成已跑满600秒。
4. 恐龙等批量结算机制必须完整跑完至少一个生产周期，再按实际入库净收益/该周期总游戏时间比较；未结算的0库存只表示当前没有入库，不代表周期效率为0。固定净产量目标也必须完整执行至正常结算。初始化片段、未完成批次、毛产量和API数量不能代替完整周期。
5. 计入初始化、规划、种子和材料补给、移动、成熟、无人机派发与回收、正常结算、失败与重生。首次跳跃和启动优惠单列；需要持续运行的脚本同时核对后续循环，不能只选首轮。
6. 在已声明的有限预算内完成代表seed对照，保留原始报告和错误。正常触及计算预算的连续生产报告仍可用来计算观测增长率；它不等于脚本异常失败。批量未完成、模型缺失机制或脚本错误则标记“未验证”。差距接近模型误差、启动成本或随机波动时，扩大必要样本或修正模型，结论确定前不覆盖存档。

## 放行与记录

| 结果 | 仓库处理 | 真实存档处理 |
| --- | --- | --- |
| 正确且效率严格更高，证据足以区分误差 | 保存候选、效率报告和来源 | 在任务授权及idle等既有约束内，才可覆盖对应已有文件 |
| 同效迁移或相同算法尚无提速 | 可保存有来源的功能实现，明确同效或待验证 | 保留现有文件 |
| 更慢、失败、模型不支持或对照不足 | 记录原因，继续本地研究 | 保留现有文件 |
| 无对应已有文件 | 保存来源及本地效率结果，优先与成熟来源比较 | 新增文件仍按存档边界单独授权 |

效率报告就近保存在对应脚本文档；多脚本迁入可统一记录到 `docs/functional-validation.md`。至少包含候选及基线哈希、源算法、完整初始条件、seed、目标/窗口、结束原因、目标净增长、游戏时间、吞吐、模型边界和是否允许替换。更快来源的历史成绩不能填写成当前候选的本地结果。

这些规则覆盖通过 `test.py`、`simulate.py`、生成入口或其他包装执行的脚本和依赖。临时覆盖也属于存档替换。排行榜还须满足[共用打榜方法](leaderboards/README.md)的实机门槛；满足其中一条不代替其余条件。
