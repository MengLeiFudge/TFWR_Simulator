# Leaderboard Scripts

这个目录承载两类长期资料：

- `lb_*.py`
  - 具体榜单脚本真源
  - 只保留当前确认最快的可执行策略
  - 固定记录一个完整轮时间注释；长说明、版本演进和候选对比不要放在这里

- `lb_*.md`
  - 具体榜单的策略文档
  - 承接目标、基线、版本结论、失败对照、下一步方向、候选策略和每个版本的大致时间

`lb_start.py` 例外：

- 它是部署时生成的入口脚本
- 仓库 `lb_start.py` 记录入口、成功条件和历史 `#1/当前版本复跑`；公开成绩以自动生成的 [排行榜成绩与提升空间](leaderboard_targets.md) 为准。缓存刷新只读取右侧复跑列，不使用左侧历史 #1
- 当前版本完整打榜正常结束后，同步 `lb_start.py` 右侧成绩和同名 `lb_xxx.md` 的证据；运行 `refresh_leaderboard_cache.py --offline` 更新比较报告。旧最好保留在策略文档，不用短时筛选或模型预测替换游戏打榜时间
- 存档内实际运行的 `gamesave/lb_start.py` 仍是部署生成物，只保留当前要跑的目标入口，不作为长期记录来源
- 除上述索引表用途外，`lb_start.py` 不属于具体榜单的长期策略真源
- 不需要也不应配套 `lb_start.md`

当前各榜的#1/#10及本地预测、短时实机、完整打榜三类时间见[排行榜进度](leaderboard_progress.md)。每次阶段交付后，由协调会话依据对应版本的记录更新；缺失项保留`—`，不混入旧版成绩。

研究先推进单项榜，再将成熟方法迁入快速重置。单个候选结束或实机暂时阻塞时，继续其他榜的本地研究；只有逐榜分析后均无合适方向才停止。当前横向分析见[策略研究优先级](strategy_review.md)；随机数的实机对照和模拟边界见[随机数对齐研究](../../mechanism_model/randomness.md)。

## 共用打榜注意事项

以下内容承接并改写自历史提交 `00f01b30` 中 `AGENTS.md` 的 `## 第二阶段优化器关注点`，但语境已经切换到当前真实游戏 oracle workflow。

### 策略选择与淘汰

每次开始一个榜、收到新的优化方向，或阶段结果不足以支持继续投入时，先完成本节，并将判断写入对应 `lb_xxx.md`。用户指定方向时，说明它解决什么问题、为什么值得投入，同时保留用户明确要求的目标和约束。

1. 列出当前能识别的不同策略方向，先不因直觉认为效率低而删去。至少检查收益机制、世界规模、任务拆分与并行方式、收益兑现路径；已有脚本只是候选之一，不能成为默认保留的框架。
2. 逐项核对机制前提。与已知规则冲突的方向立即判不通过，写明证据并停止投入，不为已知不可能的方案编写探针。只有关键前提确实未知时，才保留一项有界验证。机制不成立、某次实现错误、策略耗时过高分别记录。
3. 对机制可行的方向先做闭式计算或近似预算，计入初始化、定位、材料、移动、成熟、同步和结算等必要成本。无法估算的关键部分才做最小本地验证。理想下界、带假设的粗估、短程外推和完整目标模拟分别标注，不能互相代用。
4. 主要对照当前公开#1，结合前排成绩分布判断合理目标；DLC参与人数少时优先观察前3或相近前排，不固定以#10为目标。保留来源、抓取时间与合规依据，不以疑似漏洞成绩要求复制漏洞，也不以相对旧脚本的提速替代与目标的差距。
5. 每个可行方向记录预期收益、置信度（高/中/低）及证据、验证成本、继续与淘汰条件。置信度依据规则证据、模型覆盖与观测支持，不能只凭接近榜一的乐观估算。比较后选择少数最值得投入的方向，才编写完整策略并优化细节；实机仍须满足下节准入要求。
6. 阶段结束重新评估所选方向的收益和置信度。前提被推翻、完整成本超出预算或连续无有效进展时，回到方向比较；不能只追加局部优化。可迁移的方法及时更新本共用文档，各榜的具体证据和淘汰记录归对应 `lb_xxx.md`，草稿只保留引用与进行中的工作。

各方向的最小记录包含：方向与目的、替代方向、机制判定及依据、完整目标耗时粗估与假设、距#1的差距、收益置信度及依据、最小验证、停止条件、当前结论。未验证项明确写“待验证”，不填成已通过。

### 固定效率闭环

游戏更新后先按[更新机制对齐](../../mechanism_model/local_simulator/game-update-26385848.md)确认本版变化，并参考[规则核对的历史证据](current_game_rules.md)检查初始条件。构建26385848的16榜本地与实机配对状态见[本批复验](game-update-validation.md)。旧算法和旧成绩只作历史参考；正式榜随机样本差异与同seed模拟误差分别记录。

每个榜单进入策略优化前，都按同一套闭环处理：

1. 先只查询当前研究榜单的公开成绩，记录#1来源和抓取时间，不做全量刷新。以完整目标的本地模拟时间对比#1，并核算主瓶颈和动作预算。打榜文件进入实机的硬门槛是 **本地模拟预估时间≤对应榜单公开#1的1.5倍**；唯一豁免是用户明确要求实机运行某个具体脚本。泛指优化某榜或长期迭代不构成豁免。缺少有效#1或完整目标模拟结果时继续本地研究。
   反推结果必须落到主机制指标，而不是只写“要更快”。常见换算包括：
   - companion 榜：每次有效伴生收获必须多快、允许多少次 reroll、support 维护成本能占多少。
   - Dinosaur：1023 个 apple 的总动作预算、每阶段平均移动数、前期吃 apple 的冗余空间。
   - Cactus：行 / 列排序允许的 swap、move、measure 数，以及相对目标成绩的排序动作冗余。
   - Maze：每个节点、chunk、treasure 的路线成本和重复探索预算。

2. 完成上节策略选择与机制淘汰后，再用本地模型筛选保留方向。
   已有正式模型时优先用 `mechanism_model/`；没有正式模型时，把一次性理论探针放进 `.codex/tests/*.py`，并设置规模、时间上限和早停条件。本地模型只负责判断方向是否接近目标预算，不替代真实游戏结算。

3. 候选必须解释它如何靠近预算。
   可以是减少移动步数、提高 companion 命中率、压缩排序交换数、改善 worker 布局、减少等待成熟时间，或让早期收益更早发生。解释不清主瓶颈的候选，不进入真实游戏枚举试错。

4. 按瓶颈决定解释器费用优化的优先级。
   C# 动作模型默认不计 Python 解释和廉价判断耗时；Python 农场模拟器已计入脚本操作和调度成本，已验证范围与剩余差异见[验收记录](../../mechanism_model/local_simulator/validation.md)。候选应记录调用密度。写实现时直接采用[解释器计费与节时写法](interpreter_cost_notes.md)中语义等价的便宜表达式，计入初始化与恢复。若规划或解释器操作已是主要费用，可以优先开展专项压缩，无须先接近某个排名。阶段日志使用 `quick_print()`（0t）；`print()` 会消耗约1游戏秒。

5. 实机前逐候选核对准入证据：脚本版本、完整目标模拟seed及时间、#1来源与抓取时间、两者比值，或用户明确指定运行该脚本的授权。硬门槛同时约束短时筛选、完整统计和迁入后的复验；通过test.py、simulate等入口运行打榜文件也不能绕过。只比旧版更快、已经开始运行、希望校准模型，都不构成豁免。未达门槛继续本地算法研究。已获准实机运行时，在不相交范围推进有界本地研究，不只等待。
   如果真实结果和本地模型冲突，以真实结果为准，并回头修正模型口径或把失败原因写入对应 `lb_xxx.md`。

### 共用策略原则

1. 先研究决定 leaderboard 成绩的收益结构，不先做语法级微调。
   如果一个榜单的主收益来自 companion、连通块、全图并行、或某个特殊结算倍率，就应先围绕这个主收益设计路线，而不是先卷局部 tick 小优化。
   差距大时主动寻找新算法，核算动作下界、有效产出和串并行成本，再决定布局、路径、收益兑现或并行方式。旧结构的乐观下界仍超过#1的1.5倍时，转向结构性改进；局部改善可留作本地候选，不得因此进入实机。正确性失败或完整费用不支持改善的候选及时关闭，保留失败证据。

2. 伴生、高倍率机制、版图布局、路径和回访节奏通常优先于局部实现细节。
   对支持 companion 的 `hay`、`wood`、`carrots` 及其 Single 榜，满级约 `160x` 倍率下，生产性成熟收获必须兑现伴生。初始化清场、失败重抽和未成熟移除单独计数，不混入有效收获；出现成熟收获失配须记录并解决，不能因为总时间改善就默认接受。`fastest_reset` 按各阶段实际科技核算升级和兑现成本，不机械套用满级要求。对不支持伴生的作物或特殊机制，按自身结算机制研究。

   有效伴生产能还须扣除 reroll、support 准备、移动、等待与跨无人机改写的成本。伴生兑现是生产约束，不等于任意兑现方法都足够快；候选仍须通过目标周期预算。

   当前 Save0 的多无人机脚本 API 只把 `spawn_drone()`、`wait_for()`、`has_finished()`、`max_drones()`、`num_drones()` 暴露给脚本；没有可用的 `get_drone_id()` / `send()` / `receive()`。反编译 `Core.decompiled.cs` 中虽然残留 `Send()` / `Receive()` / `GetDroneId()` 方法体和 reset unlock 名称，但 `BuiltinFunctions.functionList` 没有注册这些函数，真实 `gamesave/__builtins__.py` 也没有定义它们。后续 companion helper / 接力设计不能按消息通信或全局共享队列成立；只有当前 Save0 明确暴露通信 API，或找到不需要运行时通信的物理同步结构，才重新打开这类候选。

   2026-06-09 已把 `carrots` / `hay` 的 `spawn_drone() + wait_for()` helper、非通信定时 helper、world-state mailbox / physical relay 都做过预算或实机筛选：只要 anchor 需要阻塞等待、用实体格编码请求 / 完成状态，或为了 helper 减少常驻生产无人机，成本都会高于当前 reroll / 并行吞吐。后续所谓“物理同步结构”必须明确证明不需要 anchor 等待、不需要编码坐标 / 完成信号，并且不会降低 active worker 吞吐；否则不进入真实游戏验证。

   同机管理多个生产位时，可把请求按支撑格排队，选择最早请求的类型并激活当前队列中同类型成员；这一批全部实际收获前保持支撑不变。每个生产位只保留一个未完成请求，后来请求进入下一批，避免陈旧请求和跨批误兑现。多机必须同时保证生产与支撑格唯一写者；跨区域请求的重抽、队列空访、实际种子资金和成熟成本都要计入。该结构已在单机胡萝卜、单机木头及多机木头通过完整实机，多机胡萝卜的同类4×8布局则未过性能门槛；逐榜证据见各同名文档。

3. 依赖 companion 的简单策略必须先过理论周期门槛。
   对 `hay`、`carrots`、`wood` 这类资源榜，先用当前基线和阶段目标反推有效伴生收获周期。满级收益按 `Growable.YieldFactor`：作物升级为 `2 ** (level - 1)`，companion 为 `5 << polyculture_level`；常见满级为 `512 * 160 = 81920` 倍基础掉落。先估算期望动作数，与同版本基线相比没有收益依据的分支不进入实机。
   例：固定外围 support 时，原地 reroll 的期望只取决于 companion 坐标和类型命中率；而“命中后走出去补种 support 再回来”至少包含往返移动和种植，平均常常超过 5 次 `200t` 操作。若原地 reroll 平均只需要约 2 次失败重刷，这类移动补种路线可直接判为弱候选。
   理论枚举必须先限规模：优先列少量手工形状、用闭式估算剪枝，再对少数候选精算；不要对整张小图的全部组合直接做精确 TSP / 全排列搜索。预计超过 `60s` 的枚举必须写成 `.codex/tests/*.py` 或正式测试脚本，带候选数量、时间上限和早停条件，不要用匿名 `python3 -` 长跑。

4. 世界大小和版图布局通常是第一优先级决策变量。
   默认世界大小不一定是最优解；应主动评估小图降移动成本、大图拉高并行吞吐、穿边、跨边界 companion、块划分等收益。

5. 复杂机制路线必须和低调度成本吞吐路线做基线对照，但不能把低伴生基线误当成资源榜主线。
   `wood` 的 `main3` 这类低复杂度、低寻路、低协调、全图并行的暴力吞吐路线，可以用来量化寻路、claim、support 初始化、reroll、等待和跨无人机协调成本；但对 `wood`、`hay`、`carrots` 这类 companion 收益主导的资源榜，低伴生路线只算弱基线或反例，不能替代生产收获全部兑现伴生的主线设计。该经验不应直接套到 `maze` / `dinosaur` 这种核心目标由特殊状态机或路径目标决定的榜单。

6. 必须明确区分 `200t` 操作和 `1t` 判断的成本模型。
   默认优先“多判断、少误操作”。只有当主流程已经稳定、判断不再明显减少昂贵动作时，才考虑进一步削减这些廉价判断。

7. 水、肥、重种、reroll、support 改写都要按收益 / tick 成本评估。
   这些动作不能因为“可能有帮助”就默认加入；应明确它们试图解决什么瓶颈，以及实际是否值得。

8. 不同 leaderboard 的目标函数和瓶颈不同，不能硬套统一模板。
   `fastest_reset`、`maze`、`pumpkins`、`sunflowers`、`wood` 的最优策略结构很可能完全不同；先识别主瓶颈，再决定搜索空间。

9. 验证节奏必须分层。
   先满足实机准入硬门槛。获准运行后，首轮按资源与阶段日志判断方向；完成轮后以均值为主。早筛至少观察两轮，最近两轮差异超过10%则增加轮次；筛选通过后继续完整运行至一次打榜正常结束，才确认最快或更新正式成绩。`--max-leaderboard-runs 0`关闭按稳定轮次停表，不构成准入豁免。
   运行中主要读 BepInEx `LogOutput.log`，结束后读取游戏 `output.txt`，并检查 Unity `Player.log`。`--request-only` 只投递，调用者负责监测、停止和按 ID 确认终态；常规等待模式自带监测。状态文件只确认控制状态。
   第一轮的 `progress_estimate` 明确带 `prediction=true`，`progress_percent` 是目标库存比例。比较成绩用 `estimated_total_game_seconds`（本轮总时间）；`eta_game_seconds` 是剩余时间，不能拿它直接和整轮基线比较。`eta_real_seconds` 只估电脑占用时间。
   库存非线性、消耗或批量结算会使 ETA 不成立；Cactus/Dinosaur 收获前可能一直 0%，需看阶段进度和动作预算。Fastest Reset 不使用资源比例。连续 30 秒无模组日志时停止并诊断；仅有快照心跳不证明策略有产出。
   官方完整统计累计约 7200 游戏秒。`simulate()` / `leaderboard_run()` 速度参数只是上限，现实速度受计算负载影响，不能用墙钟比较策略优劣。收口以 `--status-only` 检查 idle 和 `process_guard`，清理本任务残留探针。
   请求投递前完成备份和部署，直至终态确认并回到 idle，冻结真实 Save0 / gamesave 内全部 `.py`，包括入口和依赖；恢复也须等运行结束。期间可在不相交范围修改仓库内其他榜并做有界本地模拟，不能同步进游戏。

10. 探索阶段必须有详细时间统计。
   脚本进入真实验证前，应先设计好阶段日志，至少能定位最大时间来源，例如初始化、解锁、support准备、reroll、等待成熟、移动补种、收割结算、资源补给等。`quick_print()`不消耗游戏tick，`print()`会消耗约1游戏秒；日志参数计算和判断仍须计费。保留足够的探索可观测性；根据实际调用密度与收益决定是否删日志、减判断。阶段日志和模型校准需求不能豁免实机准入门槛。

11. 长流程验证应允许动态停表。
   脚本应主动打印足够细的阶段日志，例如阶段名、`time=`、关键资源、无人机数、目标值。代理验证时可以根据这些日志判断方向已经明显无效、已经达到目标、或需要切换探针，并提前停止；不得机械等待外层 `1min`。如果提前停止，必须把停止依据写成“游戏内阶段时间 / 资源进度 / output stall”，不要写成单纯墙钟耗时。

12. 真实游戏结果优先于仓库内推断。
   真实游戏结算仍是最高优先级；`output.txt` 承接请求结束后的脚本 `print()` / probe 证据，`LogOutput.log` 承接运行中的 leaderboard 完成轮、summary、`item_snapshot` 和模组错误，`state.json` 是控制面证据，只确认请求是否 `running` / `done` / `failed`。如果 `output.txt`、`LogOutput.log`、真实存档行为与当前脚本推断冲突，应优先修认知，而不是硬保留旧结论。

13. 所有魔法数字都必须注明来源。
   来源至少应指向以下之一：
   - 真实游戏常量
   - 反编译源码
   - probe 实测结果
   - leaderboard 基线数据
   - 明确的成熟 / 回访节拍推导

14. 失败路线也要长期留档。
    已经验证明显偏慢、冲突过高、收益不足的方向，应写进 `lb_xxx.md` 的“失败对照”，避免后续重复试错。

## 外部候选 `.py` 评估流程

这套流程适用于用户提供新的外部存档脚本、参考脚本、别人榜单脚本，或在 `Save0/` 参考目录里发现新的 `.py` 文件。

1. 先读取脚本内容，再判断它是什么。
   不允许看到文件名像 `lb_xxx.py` 就直接运行。必须先确认它是打榜入口、被打榜入口调用的目标脚本、普通测试脚本、工具库，还是混合脚本。

2. 先修运行入口，再修策略目标。
   如果是打榜候选，应改造成通过已有 `lb_start.py` 和已有 `lb_xxx.py` 运行；如果是测试候选，应改造成通过已有 `test.py` 运行。发现目标条件明显不符合榜单，例如 `wood.py` 用 `Wood > Hay` 提前退出，不能直接判死刑，应先把目标改成真实 leaderboard 目标再复测。

3. 禁止把外部依赖直接新增进真实存档。
   外部脚本依赖 `utils.py`、`move_utils.py` 等文件时，应读取依赖内容并把必要逻辑内联或迁入仓库真源；真实 `Save0` / `gamesave` 只能覆盖既有文件内容，不能新增、删除依赖文件。

4. 先核对实机准入，再使用“首轮估算 + 稳定均值 / 完整统计”。
   使用上文的分层验证与日志口径。通过短时筛选的候选须完整打榜结束后才替换最快真源；`finished=false runs=... average=...` 是取消摘要，可能含未完成轮，短时打榜测试时间只认新增 `[lb_xxx] run=... time=...`，游戏打榜时间取完整结束的官方统计。入口问题与策略效率问题分开记录。

5. 失败结果要分清“脚本坏”和“策略弱”。
   入口不对、目标不对、缺最后 harvest、没有触发 leaderboard 结算，这些属于脚本适配问题，应修复后再测；修复后仍慢，才记录为策略失败。

6. 更快的候选必须做复盘。
   只记录成绩不够，必须在对应 `lb_xxx.md` 里写清楚为什么更快、它打破了当前哪条假设、之前的搜索空间哪里收窄错了、这条经验能否迁移到其他榜单。如果经验可迁移，应同时抽象到本 README 的共用注意事项。

7. 迁入真源后必须再验证一次，仍须满足实机准入规则。
   外部脚本在真实存档临时覆盖里跑通，只能证明候选有效；迁入 `references/leaderboard_scripts/lb_xxx.py` 并通过同步工具部署后，还要再次真实验证，确保真源版本和临时版本一致。

## `lb_xxx.md` 推荐模板

每个榜单 md 建议统一包含以下栏目：

1. 榜单目标：资源量、单/多无人机、当前合规基线与阶段提速目标；公开参考成绩的来源及抓取日期，选择参考的理由和估计位置。
2. 当前基线：脚本版本或哈希、游戏版本/程序集、实测日期和请求 ID。
3. 策略选择：按[策略选择与淘汰](#策略选择与淘汰)记录各方向的判断、收益置信度、证据和选择理由。
4. 机制预算：核心动作数、收益倍率、初始化/等待/`1t` 假设。
5. 本地预测：候选变化、模型命令、seed/样本数/上限、完成率和动作指标；明确未模拟项。
6. 真实验证：独立保存短时打榜测试和完整游戏打榜的部署版本、请求 ID、有效完成轮数、均值和波动、结束状态及两日志证据；提前停止需说明原因。
7. 结论与失败对照：模型与实机是否一致，是否替换真源，失败机制和可迁移经验。
8. 下一步候选：标明猜测/待验证，写最小验证与停止条件。

每个候选版本独立保存以下三类时间，单位统一为游戏秒。缺项标“未取得”（结构化记录用 `null`），不得互相代填：

| 时间名称 | 取值依据 | 必留证据 |
| --- | --- | --- |
| 本地模拟预估时间 | 相同脚本和场景下，指定 seed 样本的模拟均值 | 模型版本、场景、seed、样本数、脚本 SHA、本地报告 |
| 短时打榜测试时间 | 筛选请求中真实完成 `run=` 的均值 | 请求 ID、完成轮数、范围、停止原因、部署 SHA |
| 游戏打榜时间 | 一次完整正常结束的官方最终统计，`finished=true` 且 `full_statistics=true` | 请求 ID、完成轮数、最终统计、部署 SHA、双日志 |

三类记录均附日期和游戏版本指纹。轮内 ETA 另标预测；取消摘要不进入游戏打榜时间。多次完整统计逐次保留，当前版本采用迁入真源后重新部署的完整复验；官方最终值与逐轮日志重算均值有舍入差时，保留各自来源，不混写。不同 seed 的均值差不能直接当作同 seed 模型误差。

完整示例见 [Cactus 研究记录](lb_cactus.md#2026-10-22-研究记录样本)；三类时间记录见 [Sunflowers Single](lb_sunflowers_single.md)。本机日志路径作为证据附件，核心数值与结论直接写进 `.md`，避免只能依赖临时文件恢复。

“候选策略方向”使用[策略选择与淘汰](#策略选择与淘汰)的最小记录，与已验证结论分开；不得只列脚本版本和相对旧版的提速。

## `lb_*.py` 注释边界

每个具体 `lb_xxx.py` 必须使用固定结构：

1. 第一行固定为 `from __builtins__ import *`
2. 紧接单行完整轮时间注释，例如 `# 0:37.265`
3. 第一个函数固定为 `def lb_xxx():`，名称与文件名 stem 一致，并直接承载当前最快策略流程
4. 入口函数之后才放工具方法、辅助拆分方法和当前路线必需常量
5. 文件尾固定：
   - `if __name__ == "__main__":`
   - 缩进调用同名入口函数

`lb_*.py` 可以保留：

- 与实现强绑定、不贴着代码就难理解的少量说明
- 当前脚本版本对应的单行完整轮成绩
- 关键魔法数字来源说明

`lb_*.py` 不应继续保留：

- 长篇版本演进史
- 成段优化思路
- 失败路线复盘
- 通用方法论
- 大段“当前建议 / 下一步方向”
- `mainX` 历史候选实现、接近候选实现和 wrapper 入口

`lb_*.md` 负责承接这些被移出的内容：优化经验、方向、失败对照、接近候选、多轮 / 完整统计依据，以及每个版本的大致时间。
