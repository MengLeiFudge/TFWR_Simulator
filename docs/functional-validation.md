# 功能脚本来源与本地效率

本批将功能初版恢复为全科技实现：5项沿用用户原功能脚本，其余优先迁入成熟排行榜算法。20个入口已完成本地模拟；木材修正后的有效结果使用30秒现实预算采样，早先含游戏语法错误的600秒数据已撤回。连续产出按库存净增长/实际游戏秒衡量；恐龙另做双方完整单轮对照。当前21个功能模块已由用户迁入Save0，木材第86行修复已同步到该已有文件。

长期准入见[游戏脚本验证](script-validation.md)，入口与材料要求见[功能目录](../scripts/functional/README.md)。[固定窗口证据](functional-validation.json)保存初始科技、源码与依赖哈希、实际时间、库存净变化及模型边界；[实际时间与完整周期证据](functional-rate-validation.json)保存30秒采样、自然结束的完整周期和木材语法修复。

## 计量规则与场景

连续生产可以先给30秒现实计算预算。比如实际推进100游戏秒、物品净增1e8，观测效率就是1e6/游戏秒。计算预算到即停止并报告，无须放宽预算凑固定游戏时长。样本包含从启动到停止点的全部成本，初次Jump和启动成本需与后续循环区分。

恐龙等批量结算必须完整完成至少一轮，再用实际入库净收益除以完整周期时间。未结算的0库存不代表周期效率为0。脚本异常与正常触及预算分别记录；后者仍能提供连续生产的观测速率。规则不要求模拟器自动识别各脚本的生产周期，使用者必须按机制核对结算和输出。

本批对照条件如下：

- 科技使用 `preset=all`，包含全部基础及DLC科技；32×32农场、32台无人机，普通地下地形，seed=1。
- 目标物品初始库存为0，其他物品各1e9；目标设为1e15，防止旧入口因达到固定目标停机。
- 记录实际游戏时间，包含初始化、规划、移动、成熟、派工、同步、重生、结算和真实资源消耗。非目标库存预先备足，未计入生产这批初始材料的时间。
- 原对照冻结了23个实际Save0功能文件，它们与提交 `5244c86` 的对应源码AST相同，测量完成时23份哈希均未变化。这里“存档版本”指该历史冻结基线；当前存档已更新为本批功能实现，当前哈希见实际时间数据。
- 下表的600秒结果已经实际跑满，作为统一参考；600秒不是后续效率验证的硬门槛。API边界可能略超600秒，倍数使用各自真实结束时间计算。

## 连续生产：有限现实预算的直接报告

水稻和修正后的木材均设置30秒现实预算，没有游戏时长目标。模拟器在预算停止时直接返回以下结果：

| 实现 | 实际游戏秒 | 库存净增长 | 净增长/游戏秒 |
| --- | ---: | ---: | ---: |
| 水稻：冻结存档版本 | 126.362537 | 39,936 | 316.0430 |
| 水稻：迁入用户原算法 | 289.262569 | 4,358,144 | 15,066.3946 |
| 木材：冻结存档版本 | 244.335561 | 2,080,208,384 | 8,513,735.6713 |
| 木材：恢复原材料判断后 | 286.224197 | 11,019,695,104 | 38,500,221.8926 |

各样本推进的游戏时间不同，分母分别使用自身实际值。水稻约47.67倍、木材约4.52倍描述对应观测段的净增长率，不能写成已经运行600秒或无限运行后的产量。木材的条件修复及本地语法检查见[游戏语言静态检查](../simulator/local_simulator/syntax-validation.md)。

新增报告字段为 `efficiency.elapsed_game_seconds`、`efficiency.items.资源名.net_change` 与 `net_per_game_second`。进度同时输出目标物品的 `goal_net_gain` 和 `goal_per_game_second`。负数表示净消耗；游戏时间为0时增长率为null。正常预算停止仍保留效率，父进程强制终止且没有世界快照时无法计算。

## 恐龙：完整一轮对照

本地有限入口分别调用存档的 `collect(当前Bone+1)` 与候选的 `production_cycle()`。前者至少执行完整一轮，后者就是迁入的排行榜生产周期；都经换帽正常结算后返回，保留原算法和依赖，不提前砍尾。两份入口均正常完成，日志含 `completed_cycle`，没有脚本错误。

| 实现 | 完整轮游戏秒 | 实际净增Bone | Bone/游戏秒 |
| --- | ---: | ---: | ---: |
| 存档版本 | 2,469.471648 | 33,488,928 | 13,561.1713 |
| 排行榜算法 | 775.380755 | 33,488,928 | 43,190.3008 |

同一收益下候选约快3.18倍。600秒时双方都未结算；此前1800秒库存记录仍保留为进度证据，不据此把存档完整周期的效率判为0。完整轮结果才是本项效率依据。

## 算法来源与必要适配

- `bamboo.py`、`mushroom.py`、`dynamite.py`逐字节迁入用户桌面目录的原算法。`rice.py`与`coal.py`只将原顶层连续循环封装为同名入口；Coal的 `first`、`round` 保留原模块绑定。
- 地表资源、迷宫、向日葵、恐龙分别迁入对应多机排行榜实现，保留布局、任务拆分、路径、同步、成熟队列和关键参数，移除排行榜固定库存终点。运行时不依赖排行榜目录。
- 金字塔保留 `lb_pyramids.py` 的单塔修补、分层同步和中心补尖；首次Jump，后续普通田使用浅层钻头，深度48前换回采矿帽。实际600秒内完成16次修塔结算，净Power已扣除消耗。
- 藏宝图保留 `lb_treasure_map.py` 去环路径；加入Jump和浅层钻头，按玄武岩的实际z定位另一列地图。普通田没有对应层时有界重生，连续8片无收益后停止。
- 矿物使用 `lb_ores.py` 的按列派工与沟挖，普通全科技田加入Jump及爆破钻头，共用 `mining.py`。重置榜单机收集方法在本次对照中明显更慢，已淘汰。
- 怪异物质提取 `lb_fastest_reset.py` 的并行伴生树苗圃；功能初版固定全科技路径，不迁入科技购买流程。
- 水和化肥由游戏自动获取，对应功能脚本已移除。旧低科技补给框架 `farm_support.py` 已撤出功能目录。

原作者、commit和许可见各脚本头及[功能目录说明](../scripts/functional/README.md)。完整源文件与候选SHA256见JSON；本地原文、冻结存档、源算法与原始报告在 `.codex/functional-fulltech-20261108/`。旧仓库基线可从提交 `5244c86` 恢复。
