# 排行榜策略与研究记录

本目录保存30份同名榜单策略文档、共用研究方法及一份进度总表。当前可执行实现位于[scripts/leaderboard](../../scripts/leaderboard/README.md)，被替换版本和未采用候选位于[历史代码库](../../references/leaderboard_history/)。单榜结论写回对应`lb_xxx.md`，不再新建阶段、日期或验证批次文档。

## 排行榜状态汇报

用户询问排行榜时，回复与[进度总表](leaderboard_progress.md)统一使用七列，顺序固定：

| 排行榜 | 实机 | 模拟 | #1 | #3 | #10 | 改进方向 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 榜名及单／多机 | 账号最高时间（#排名） | 已有最好有效模拟 | 公开第一名时间（差距%） | 公开第三名时间（差距%） | 公开第十名时间（差距%） | 下一步具体机制或瓶颈 |

- #1、#3、#10取对应公开排名；不足3人或10人时，相关列显示末名时间、差距及排名，例如`9:10.000（+50.0%）（#8，末名）`，百分比按该末名时间计算。空榜或缺失数据写“未取得”。所有榜以#1为目标，#3、#10与前排分布用于判断可实现水平。
- “实机”只指当前账号在该公开榜上的历史最高记录，并附排名。本机最近完整统计、最好单轮、短筛和缓存估位另记，不能代填账号记录。确认无记录写“未上榜”，查询失败且无可用旧值写“未核实”。
- “模拟”取已有更快的有效本地目标时间，允许未采用实现及短程外推，不附“候选”或†等符号。对应单榜页必须记录版本、seed、实际窗口、进度、推算方法和未覆盖部分；失败退出的经过时间不是完成时间，批量机制至少兑现一个完整周期。
- 基准时间取有效实机、有效模拟中较快者；仅有一种有效时间时用该值。#1、#3、#10时间后各附`(基准时间 / 该名次时间 - 1) × 100%`，保留一位小数与正负号，正数表示我们更慢，负数表示我们更快。例如基准150秒、#1为100秒，显示`1:40.000（+50.0%）`；基准50秒、#1为100秒，则显示`1:40.000（-50.0%）`。两种有效时间均缺失时只显示公开时间。排序、阶段目标及实机准入继续按相对#1的差距判断，2倍对应`+100.0%`。
- 时间显示为累计分钟、秒和毫秒，比例用原始精度计算。改进方向写机制、分工或主成本，不只写“继续优化”。
- 榜单事实、账号状态及各自查询时间归[公开缓存](../../references/leaderboards/leaderboard_cache.json)；逐榜来源、日期和刷新失败信息归[公开快照](../../references/leaderboards/status_snapshot.md)。离线重建保留原抓取时间，表格单元格不重复添加“历史缓存”；使用旧缓存时在来源说明其时效。

单榜研究只刷新该榜；用户查询全榜时刷新全部30榜，默认前100名。修改本地结果或方向后，更新`leaderboard_progress.json`并运行：

```bash
python3 game_control/tools/refresh_leaderboard_cache.py --script lb_maze
python3 game_control/tools/refresh_leaderboard_cache.py --offline
```

工具只生成进度总表与公开快照两份Markdown。参数和代理设置见[排行榜缓存](../../game_control/README.md#排行榜缓存)。阶段顺序见[三阶段计划](strategy_review.md#三阶段计划)。

## 共用打榜注意事项

### 策略选择与淘汰

每次开始一个榜、收到优化方向或结果不足以支持继续投入时，先回答“为什么做这个方向、还有哪些方向、预计收益和置信度如何”，将判断写入对应单榜页。用户明确指定尝试机制可行的改动时，完成最小候选与本地对照；除非已有同条件失败证据，不以收益小或仍需找路线为由跳过。

1. 先列不同收益机制、世界规模、任务拆分、并行方式和结算路径。现有脚本只是一个方向。算法按维护的状态、允许的变形和恢复条件区分，名称相似不能证明已经覆盖。
2. 核对机制。与已知规则冲突立即淘汰并注明依据；仅未知前提才做有界验证。机制不可行、实现错误、耗时过高分别记录，不为已知不可能的方向编写探针。
3. 对可行方向做闭式或近似预算，包含初始化、定位、供料、移动、成熟、同步和结算。理想下界、条件估算、短程外推和完整模拟分开。记录距当前#1的差距、收益置信度及依据、最小验证与停止条件，再选少量代表深入。
4. 较好时间仍超过2×#1时，优先重列方向和主机制，不在原框架无界调参。用户明确指定细化现有算法时，执行其范围并采用有效改善。失败只排除实际验证的前提或构造，不将样本数当作覆盖证明。
5. 改动组合后重新比较完整费用，不把独立提速相加。阶段无进展时检查尚未覆盖的状态表示与恢复构造，必要时查外部源码并记录来源、版本、许可和已读范围。选择依据或通用方法变化时同步正式文档，草稿只保留进行中状态和引用。

### 重置榜的科技路线计价

两项快速重置均先按资源速率确定大致路线，再写完整脚本。由最终付款倒推生产方式、真实API要求和最低资源，必要前置与可选投资分列；科技树UI父连线及普通Reset前缀不是地下Reset的必经链。

1. 建立按时间排列的资源账，包含最终付款、必要解锁、可选升级、种子／勘探消耗、阶段库存和终点余额。`unlock`可不检查UI父项，但附加条件仍须满足。
2. 混合获取必查：采x附带y时，记录联合净产量、科技、机器数和可用时点。后续缺口扣实际副产物，删除生产也扣其副产物；不能重复计算时间或把末段库存倒用到前期。水肥自动积累、感染联产同样入账。
3. 明显余量同时比较“少采省多少”和“提前／推迟投入升级省多少”，再比较组合。不为清零买无法回本的科技；整批零头、自动积累和有用副产物须说明。
4. 独立串行资源可用`缺口 / 当前净速率`估算；混采使用联合约束，可并行阶段算依赖关键路径，另计切换。升级比较新增筹资与剩余需求的`Σ需求 × (1/旧速率 − 1/新速率)`，倍率只作用于实际受影响部分；计入耗电动作和缺水肥等待。
5. 少量完整路线粗算后，用相同初始条件和预先选择的seed集配对模拟，记录科技、阶段库存和真实结算。新seed加入后按共同较大样本重比，不删失败seed报均值，不拼接阶段节省当整轮成绩。
6. 最终从零筹资并实际付款，复查漏账和余额。所有路线仍远离榜首时重新检查资源来源与可用机制。两榜的当前账目和淘汰组合分别归[普通Reset](lb_fastest_reset.md)和[地下Reset](lb_fastest_underground_reset.md)。

### 固定效率闭环

所有游戏脚本先满足[语法、正确性、效率与替换要求](../script-validation.md)。功能初版全科技，重置榜用原版初始条件。已有模型优先用[C#完整模拟器](../../simulator/headless/README.md)；简化动作模型不计完整解释器费用，不能代替完整执行证据。当前模型覆盖、误差和未覆盖部分以[验收记录](../../simulator/headless/validation.md)为准，不沿用旧Python模型结论。

- 以当前#1反推核心预算：伴生有效收获周期与重抽／支撑、恐龙move/apple、仙人掌move/swap/measure、迷宫节点与宝藏路径；初始化、成熟、同步和结算均计入。
- 理论枚举先剪枝，探针保存在`.codex/`并设置规模、时间、动作上限及早停。预计超过60秒有进度，30秒无有效输出停止缩小输入。阶段日志用0t的`quick_print()`，`print()`约耗1游戏秒，参数计算仍计费。廉价写法见[解释器费用](interpreter_cost_notes.md)。
- 有效改善先更新最快源码及单榜文档，组合后复验。存档覆盖另核对旧版、依赖、idle并备份；可用实际短程效率，不必等原目标完整结束，但批量机制须正常兑现。复制不授权游戏执行。
- 实机准入两条独立路径：用户明确授权该任务；或有效模拟≤2×当前#1且严格快于账号公开最高记录。运行前记录所用路径、源码版本、seed／窗口、预估、#1和账号记录来源与时间；自动路径缺少可比值不推定达标。规则覆盖短筛、迁入复验与包装入口。
- 获准后至少观察两轮，最近两轮差异>10%增加轮次。筛选通过继续一次正常完整统计，才记该版本游戏打榜时间。完整统计约累计7200游戏秒；短筛只认真实`run=`，取消摘要可能含未完成轮。
- 请求前部署；运行至同ID终态确认并回到idle期间冻结全部存档`.py`。运行中观察BepInEx日志，结束读`output.txt`并查Unity日志。连续30秒无模组日志停止诊断，快照心跳不证明产出。`--request-only`由调用者负责有界监测、停止和终态回收。
- 首轮资源线性增长才可外推。比较目标时间用`estimated_total_game_seconds`，剩余时间是`eta_game_seconds`，墙钟ETA仅安排占用。恐龙、仙人掌等未结算批量不能据零库存判卡住，重置榜按阶段判断。

### 共用策略原则

伴生倍率按真实`Growable.YieldFactor`及`5 << polyculture_level`计算，收益扣种子、重抽、支撑、移动和等待。初始化／失败重抽与成熟生产收获分开计数，支撑须在兑现时仍匹配。跨区域请求只能按真实收获倍率计产，不因接受时匹配就记高倍。已存在的成熟失配及其策略取舍在单榜页明确保留，新方案不能默认为正确。

无人机字典不共享；脚本API没有`get_drone_id`、`send`或`receive`。helper、物理邮箱或接力须证明写入归属、坐标传递、无阻塞和总吞吐；不能把反编译中未注册的方法体当作可用API。同机可以按支撑格与类型分批保持请求，多机还须处理唯一写者和真实种子资金。具体已失败布局查对应单榜表。

地图大小、环绕、生产密度与兑现结构需主动比较。区分200t动作和1t判断，少判断若带来更多误操作可能更慢。水、肥、支撑成熟、重种与规划均按完整收益收费。不得利用结算窗口重复收同一迷宫宝藏。

### 地下榜已验证的结构结论

| 机制 | 可复用结论与边界 | 单榜记录 |
| --- | --- | --- |
| Rice | 成功收首株后再挖干梯田、种下一Clay，使第二层成长重叠；专用场每柱只有两层，干地面不证明已收获 | [多机](lb_rice.md)、[单机](lb_rice_single.md) |
| Bamboo | 筛统一5/9花节后保桩批量切收；切花高度浇水会重置飞行高度。空道与空中心是布局选择，须核覆盖及负载 | [多机](lb_bamboo.md)、[单机](lb_bamboo_single.md) |
| Mushrooms | 共同高度带、采样柱与失配材料利用率共同约束；不能只比少移动，普通田与专用场找层范围分开 | [多机](lb_mushrooms.md)、[单机](lb_mushrooms_single.md) |
| Ores | 多机相邻沟网借邻柱降低覆土成本；单机付费勘探须实筹煤铁，最近距离可能来自不同矿，几何只是选孔依据 | [多机](lb_ores.md)、[单机](lb_ores_single.md)、[勘探机制](../block-mining.md#铁与石英勘探) |
| Dynamite | 覆盖层按实际开格推迟准备；零扩张不自动公开邻格雷层数字。固定几何可复用，盘面事实每盘重建，安全证明不等于已挖开 | [多机](lb_dynamite.md)、[单机](lb_dynamite_single.md) |
| Pyramids | 同时只修一塔，保留原沙，几何定高、清理后按八邻支撑维修；主机提前中心并最后补尖，实际缺口与人为挖空分开 | [多机](lb_pyramids.md)、[单机](lb_pyramids_single.md) |
| Treasure Map | 记录三维坐标最后出口可合法去环；索引递增、保留下降，不离开公开有效通路、不破坏未来块 | [藏宝图](lb_treasure_map.md) |
| Underground Reset | 科技、真实地层周期和副产物联合计价；普通地形产出不能直接当专用榜吞吐，特殊土仅加成种在其上的对应作物 | [地下Reset](lb_fastest_underground_reset.md) |

## 外部候选 `.py` 评估流程

先读入口、依赖、目标和许可，记录版本及已读范围；入口错误、缺收获或目标不符先适配，再判断策略。外部依赖迁入仓库实现，不能在真实存档新增依赖文件。打榜适配已有`lb_xxx`／`lb_start`，探针适配已有`test.py`。

用本地语法、正确性和完整费用对照筛选，再按上述实机准入运行。更快候选须解释打破了哪个假设，并在迁入源码后核对执行副本；新版本正式成绩取迁入复验，作者自述成绩不算本机实测。来源汇总见[GitHub](github_strategy_research.md)和[B站](bilibili_strategy_research.md)。

## `lb_xxx.md` 推荐模板

每份单榜文档固定四节，数值和机制结论直接保存在正文，原始轨迹、长哈希及批次回执留`.codex/`，不新建过程MD／JSON。

1. **当前策略与成绩**：目标和对应脚本、当前分工／状态／同步、主瓶颈；账号最高、有效模拟及本版本完整统计分开说明，注明日期、版本和模拟口径。
2. **淘汰与未采用方案**：表格列方向、实际表现、失败原因及适用范围、归档代码。机制判定与仅预算项注明未写代码，失败不扩大为整个算法类别不可能。
3. **历史正式版本演进**：按日期列核心变化、实机／模拟时间及归档文件；旧版合集中的函数可注明原入口。未注明成绩类别的旧注记不能升级为正式实机。
4. **下一步优化方向**：保留1～3个尚开放方向，写机制、收益依据、置信度、最小验证和停止条件；已关闭方向移入淘汰表。

| 时间名称 | 取值与最小证据 |
| --- | --- |
| 本地模拟预估时间 | 同脚本、同场景完整结果或实际窗口外推；记录模型、源码版本、seed、实际进度、方法和未覆盖部分 |
| 短时打榜测试时间 | 筛选请求中真实完成`run=`的均值；记录请求、完成轮、范围和停止原因 |
| 游戏打榜时间 | 一次正常完成官方完整统计；记录请求、完成轮、最终值、部署版本和双日志 |

各项附日期及游戏／模型版本；官方最终值和逐轮重算均值如有舍入差保留各自来源。不同seed均值差不等于同seed模型误差。账号最高仍独立取公开记录。

历史代码归`references/leaderboard_history/<lb_xxx>/`，旧正式版本按日期、版本号、成绩及提交号命名，候选按日期、方向及有效时间命名。失败或局部窗口的档名时间不能当整轮成绩，代码、来源路径和提交映射维护在`manifest.json`。档案不参与类型检查、部署或游戏导入。

## `lb_*.py` 注释边界

当前脚本固定：首行`from __builtins__ import *`，随后完整轮时间注释，第一个函数与文件同名，辅助函数随后，末尾`if __name__ == "__main__":`调用同名入口。只保留当前确认最快实现、少量必要注释与数字来源，版本、失败和接近候选移入对应文档及历史代码库。

仓库`lb_start.py`是入口／历史完整复跑索引，右侧列在当前版本完整统计结束后更新；存档同名文件是部署生成物。无需`lb_start.md`，短筛、模型或账号历史最高不替代该版本完整复跑。
